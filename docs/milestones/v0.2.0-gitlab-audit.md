# Milestone v0.2.0: GitLab CI/CD Audit MVP

Status: **defined, not started**. This document is a design and scope reference for
implementation. No production code exists for this milestone yet.

Predecessor: v0.1.0, the Kubernetes audit MVP, released and tagged. See
[`CLAUDE.md`](../../CLAUDE.md) for durable, cross-milestone project rules (scope
discipline, read-only invariants, testing and dependency policy) — this document adds
GitLab-specific detail on top of those rules, it does not replace them.

## A. Objective

A read-only CLI audit of a single GitLab project, on GitLab.com or a compatible
self-managed GitLab instance. It produces `report.json` and `report.html` consistent
with CloudOps Guard's existing reporting approach (see `src/cloudops_guard/reports/`):
atomic UTF-8 writes, a static dependency-free HTML report, and a JSON report suitable
for programmatic comparison.

## B. Proposed command interface

```bash
cloudops-guard audit gitlab \
  --gitlab-url <url> \
  --project <numeric-id-or-url-encoded-path> \
  --output <directory>
```

- `--gitlab-url`: base URL of the GitLab instance (e.g. `https://gitlab.com` or a
  self-managed instance's base URL). Required.
- `--project`: the target project, either its numeric ID or its URL-encoded path
  (e.g. `group%2Fsubgroup%2Fproject`), matching the GitLab REST API's `:id` parameter
  convention. Required.
- `--output`: directory to write `report.json` and `report.html` into, matching the
  existing `audit kubernetes` convention. Required.

The access token is read **only** from the environment variable
`CLOUDOPS_GUARD_GITLAB_TOKEN` (name provisional). It must never be accepted as a
`--token`-style CLI option and must never be read from a `--config` YAML file — both
would risk the token appearing in shell history, process listings, or a committed
config file. This mirrors and extends the existing credential-handling posture: v0.1.0
already never accepts kubeconfig credentials as CLI input and never prints them, even
in exceptions.

Open question for implementation: whether to also support `--namespace`-style scoping
(GitLab "namespace" means something different from Kubernetes namespace — a
user/group namespace that *owns* a project) is out of scope for v0.2.0 per §E; this
command audits exactly one project.

## C. Agreed initial checks

Severities below are **provisional** and should be revisited once real-world evidence
(false-positive rate, operator feedback) is available, consistent with how v0.1.0's
Kubernetes check severities were assigned by judgment rather than an external standard.

Check IDs follow the existing `<PLATFORM>-<CATEGORY>-<NNN>` convention established by
the Kubernetes checks (`K8S-RES-001`, `K8S-IMG-001`, `K8S-REL-001`, ...). Once
implemented, these IDs are stable per the project's durable rules and must not change.

### GL-BR-001 — Default branch is not protected

- **Condition**: the project's default branch (`default_branch` from `GET
  /projects/:id`) has no matching entry in `GET /projects/:id/protected_branches`.
- **Provisional severity**: High.
- **Why it matters**: an unprotected default branch permits force-push, deletion, and
  unreviewed direct pushes by anyone with push access. The default branch is typically
  the deployment/release source of truth.
- **Evidence (non-sensitive)**: project path, default branch name, and the fact that no
  protection rule matched. No commit content, no member names.
- **Recommendation**: create a protected-branch rule for the default branch with
  push/merge access restricted appropriately.
- **Edition/version/API concerns**: `protected_branches` is available on CE and EE,
  GitLab.com and self-managed, but the response shape (e.g. `allow_force_push`,
  `code_owner_approval_required`) has grown over time — the client must tolerate
  missing fields rather than assume a fixed schema.
- **Possible false positives**: group-level push rules or other org-level controls
  (EE) could provide equivalent protection through a mechanism this check does not
  inspect; this should be documented as a known limitation, not silently corrected for.

### GL-BR-002 — Force-push is allowed on the default branch

- **Condition**: within the protected-branch rule matching the default branch,
  `allow_force_push` (or the applicable equivalent field) is `true`.
- **Provisional severity**: High.
- **Why it matters**: force-push on the default branch can rewrite or destroy commit
  history, obscure prior changes, and break collaborators relying on that history —
  undermining any audit trail.
- **Evidence**: branch name and the boolean value only.
- **Recommendation**: disable "Allowed to force push" for the default branch's
  protection rule.
- **Edition/version/API concerns**: `allow_force_push` has historically been
  EE-gated; on CE instances (or older API versions) the field may be entirely absent
  rather than `false`. The check must treat "field absent" as "unknown / not
  applicable," never as an implicit "protected."
- **Possible false positives**: none expected once the CE/EE field-absence case above
  is handled correctly; this is largely a straightforward boolean check once GL-BR-001
  confirms a protection rule exists at all.

### GL-BR-003 — Developers can push directly to the default branch

- **Condition**: the protected-branch rule's push access levels include the
  role-based "Developer" access level (30), rather than being restricted to
  Maintainer (40) or "No one."
- **Provisional severity**: Medium.
- **Why it matters**: allowing direct pushes at the Developer role bypasses merge
  request review for a broad set of contributors, reducing change visibility.
- **Evidence**: the resolved minimum role-based push access level (name/number) for
  the matched rule. Never the list of specific users or groups holding that access —
  only the role threshold itself.
- **Recommendation**: restrict default-branch push access to Maintainer or "No one,"
  and require changes via merge request.
- **Edition/version/API concerns**: EE allows `push_access_levels` entries scoped to
  specific users or groups, not just roles. This check's scope is role-based access
  levels only; user/group-specific grants are a known gap, not evaluated in v0.2.0.
- **Possible false positives**: the permission being *granted* does not mean it is
  ever *used* — a project may have no members actually holding the Developer role.
  The check reports the grant, not observed usage; this should be reflected in the
  finding's wording during implementation so it isn't read as "a developer pushed
  directly."

### GL-MR-001 — Successful pipelines are not required before merge

- **Condition**: the project setting `only_allow_merge_if_pipeline_succeeds` is
  `false`.
- **Provisional severity**: Medium.
- **Why it matters**: without this gate, merge requests can be merged despite failing
  CI, undermining the purpose of any configured tests, builds, or security scans.
- **Evidence**: the boolean setting value and project path. No pipeline or job data.
- **Recommendation**: enable "Pipelines must succeed" in merge request settings.
- **Edition/version/API concerns**: the related setting
  `allow_merge_on_skipped_pipeline` weakens this guarantee if enabled (a skipped
  pipeline counts as "succeeded") — implementation should decide whether to fold this
  into the same finding or treat it as a separate, softer note.
- **Possible false positives**: a project with no `.gitlab-ci.yml` at all has no
  pipelines to gate on, making this setting moot rather than wrong. Whether to
  suppress or soften this check when no CI configuration is detected is an open
  implementation decision (see "Open questions" below).

### GL-CI-001 — CI job or service container image uses a mutable tag or no tag

- **Condition**: mirrors the existing Kubernetes `K8S-IMG-001` check
  (`_image_tag` / `_is_pinned_by_digest` in `src/cloudops_guard/checks/kubernetes.py`):
  a job or service `image:` reference has no tag, or uses a known-mutable tag such as
  `latest`, and is not pinned by digest.
- **Provisional severity**: High (matches `K8S-IMG-001` for product consistency).
- **Why it matters**: identical rationale to `K8S-IMG-001` — reproducibility, rollback
  safety, and supply-chain traceability, arguably sharper for CI images since they
  execute with pipeline (and potentially job-token) permissions.
- **Evidence**: job name and the image reference string with the resolved tag noted —
  never job scripts, never variable values.
- **Recommendation**: pin to a specific version tag at minimum; pin to a digest for
  the strongest guarantee — reusing the same wording pattern as `K8S-IMG-001`.
- **Edition/version/API concerns**: obtaining the *effective* CI configuration (with
  `include:`/`extends:` resolved) requires either the CI Lint API or reading
  `.gitlab-ci.yml` content directly — both mean the raw or merged YAML passes through
  the process at some point. This directly touches the "never persist raw or merged CI
  YAML" invariant (§D) and is flagged as an open design question below, not resolved
  by this document.
- **Possible false positives**: dynamic image references built from CI/CD variables
  (e.g. `image: $CI_REGISTRY_IMAGE:$TAG`) cannot be statically resolved without
  evaluating variables, which this tool must never do. Such jobs should be reported as
  "undeterminable," not guessed at. `include:`-based external CI config (from another
  project) also complicates "effective configuration" resolution; scope (local job
  definitions only, vs. following includes) needs to be decided before implementation.

### GL-SEC-001 — CI jobs are public for a non-public project

- **Condition**: project `visibility` is `private` or `internal`, but `public_jobs`
  (the "Public pipelines" setting) is `true`.
- **Provisional severity**: High.
- **Why it matters**: this setting controls whether pipeline/job output is viewable
  without project membership — a real exposure risk for a project that is otherwise
  not public.
- **Evidence**: project visibility level and the `public_jobs` boolean. This check
  never fetches job logs or output itself.
- **Recommendation**: disable "Public pipelines" for non-public projects.
- **Edition/version/API concerns**: "public" here is project-scoped; a self-managed
  instance may have its own `restricted_visibility_levels` policy that changes what
  "internal" effectively means instance-wide. This check's notion of "public" is
  explicitly scoped to the project-level `public_jobs`/`visibility` fields only, not
  instance-wide policy.
- **Possible false positives**: none especially notable; this is a fairly
  deterministic combination of two boolean/enum fields.

### GL-SEC-002 — CI job tokens are permitted to push to the repository

- **Condition**: the project's CI/CD Job Token permission settings allow the job
  token (`CI_JOB_TOKEN`) push access to the project's repository.
- **Provisional severity**: High.
- **Why it matters**: the job token is an ambient credential available to every
  pipeline job. If it can push to the repository, a compromised or malicious job (for
  example, from a dependency compromise or a pipeline triggered by an untrusted merge
  request) gains a repository-write escalation path.
- **Evidence**: the boolean/permission setting value only.
- **Recommendation**: disable repository push permission for CI job tokens unless a
  specific, reviewed automation depends on it.
- **Edition/version/API concerns**: **flagged as needing verification before
  implementation.** GitLab's job-token permission model (scope allowlists, push
  permission toggles) is among the more recently introduced and still-evolving parts
  of the API across versions; the exact field name(s) and availability by
  edition/version must be confirmed against the target GitLab API version, not
  assumed from this document.
- **Possible false positives**: legitimate automation (e.g. a bot that tags releases
  from CI) may intentionally need this permission. The finding should be worded as "a
  security-relevant configuration exists," not "this is necessarily wrong."

### GL-SEC-003 — Pipeline-variable override permissions are more permissive than Maintainer

- **Condition**: the project setting controlling who may set/override CI/CD variables
  when manually triggering a pipeline (e.g. `restrict_user_defined_variables` or its
  current equivalent) does not restrict this to Maintainer or above.
- **Provisional severity**: High.
- **Why it matters**: if lower-privileged roles can override pipeline variables at
  trigger time, they may be able to inject values into unsafely-interpolated scripts
  or override security-relevant variables — an authorization bypass risk.
- **Evidence**: the boolean/role setting value only. This check must never call any
  CI/CD variables endpoint and must never report variable names or values (§D).
- **Recommendation**: restrict user-defined variable overrides to Maintainer or above.
- **Edition/version/API concerns**: **flagged as needing verification before
  implementation**, for the same reason as `GL-SEC-002` — field name and semantics
  should be confirmed against the current API for the target GitLab version/edition.
- **Possible false positives**: none especially notable beyond version-specific field
  drift.

### GL-COST-001 — Redundant pipelines are not automatically cancelled

- **Condition**: the project setting `auto_cancel_pending_pipelines` is not enabled.
- **Provisional severity**: Low.
- **Why it matters**: without auto-cancel, superseded pipeline runs (e.g. from rapid
  successive pushes to the same branch/MR) continue consuming CI/CD compute
  unnecessarily — a cost and runner-contention concern, not a security one.
- **Evidence**: the boolean setting value.
- **Recommendation**: enable "Auto-cancel redundant, pending pipelines."
- **Edition/version/API concerns**: stable, longstanding field across CE/EE.
- **Possible false positives**: projects that intentionally want every pipeline to
  run to completion (e.g. for a complete audit/compliance run history) may disable
  this deliberately.

### GL-COST-002 — Git clone depth is unlimited

- **Condition**: the project/pipeline default Git depth setting (e.g.
  `ci_default_git_depth`) is unset or `0` (full clone) rather than a bounded positive
  integer.
- **Provisional severity**: Low.
- **Why it matters**: unbounded clone depth means every pipeline job clones full
  repository history, increasing job time and compute cost, especially for large or
  long-lived repositories.
- **Evidence**: the configured depth value, or "unset/full."
- **Recommendation**: set a bounded default Git depth appropriate to the project's
  branching/tagging needs.
- **Edition/version/API concerns**: a comparatively recent, less consistently
  documented settings field across GitLab versions — needs verification at
  implementation time. Per-job `GIT_DEPTH` overrides in `.gitlab-ci.yml` are invisible
  to a project-settings-only check and raise the same in-memory-only YAML-processing
  question as `GL-CI-001`.
- **Possible false positives**: young repositories with little history make this
  setting moot; projects that specifically need full history in CI (e.g. changelog
  generation across all tags) legitimately need unlimited depth.

### GL-REL-001 — Project job timeout exceeds a configurable threshold

- **Condition**: the project setting `build_timeout` (seconds) exceeds an
  operator-configurable threshold, mirroring the existing `--restart-threshold`
  pattern from `audit kubernetes`.
- **Provisional severity**: Medium.
- **Why it matters**: straddles reliability and cost — an excessively long timeout
  lets a hung job occupy a runner slot for a long time before GitLab kills it,
  delaying feedback and, on paid/self-hosted runners, increasing cost.
- **Evidence**: the configured timeout (human-readable, e.g. minutes) versus the
  configured threshold. No job-specific data.
- **Recommendation**: lower the project's default job timeout to a value appropriate
  for its typical job durations; use per-job `timeout:` overrides sparingly for
  legitimately long jobs.
- **Edition/version/API concerns**: `build_timeout` is a longstanding, stable Projects
  API field — the lowest API-stability risk of the eleven checks here.
- **Possible false positives**: projects with legitimately long-running jobs (large
  builds, ML training, etc.) may need a higher timeout deliberately — this is exactly
  why the threshold must be operator-configurable rather than fixed.

## D. Security and privacy invariants

- Use read-only GitLab API operations only.
- Never call project, group, or instance CI/CD variables endpoints.
- Never collect or report job traces, logs, artifacts, credentials, or tokens.
- Never persist raw or merged CI YAML in reports.
- Never reproduce CI scripts or variable values in findings or error messages.
- If CI configuration must later be processed (see `GL-CI-001` / `GL-COST-002`),
  process it only in memory and retain only the normalized, non-sensitive fields a
  check actually needs — the raw content itself is never written to a report, log, or
  intermediate file.
- Never log authentication headers.
- Sanitize remote API errors and untrusted response content before they reach a
  report or the terminal — mirrors the v0.1.0 Kubernetes collector's existing
  approach of never surfacing raw `ApiException.reason`/body/headers.
- A failure to access required information must not silently produce a partial clean
  report: if a check cannot be evaluated because required data could not be
  retrieved, the audit must fail loudly (non-zero exit) rather than omit the check and
  report as if everything else passing meant the project was clean.

These extend, and do not replace, the existing read-only invariants in
[`CLAUDE.md`](../../CLAUDE.md).

## E. Explicit non-goals for v0.2.0

- Group-wide or organization-wide auditing.
- Runner configuration auditing.
- Historical pipeline reliability analytics.
- Job-log or artifact inspection.
- GitLab remediation or write operations.
- AWS or Azure APIs.
- Database, dashboard, SaaS multi-tenancy, authentication, billing, or LLM use.
- General Kubernetes hardening, unless a concrete defect is discovered incidentally
  while working in shared code (e.g. the report generator).

## F. Planned implementation phases

1. **Minimal platform-neutral reporting/model adaptation**, preserving Kubernetes
   behaviour exactly. The current `Finding`/`AuditReport` models
   (`src/cloudops_guard/models.py`) are Kubernetes-shaped: `Finding.cluster_context`,
   `Finding.namespace`, `Finding.container_name`, and the closed `ResourceKind` enum
   (`Namespace` / `Pod` / `Deployment`) don't map cleanly onto a GitLab project
   (no cluster, no container; GitLab's own "namespace" concept means something
   different — the group/user that owns a project). This phase generalizes the shared
   models just enough to support a second platform without changing the existing
   `report.json`/`report.html` output for `audit kubernetes` byte-for-byte. The exact
   shape of that generalization (renaming fields vs. introducing a platform-specific
   wrapper) is an implementation-time design decision, not decided here.
2. **GitLab HTTP client, error sanitization, and normalized project snapshot.**
   Note for implementation: `requests` and `urllib3` are already transitive
   dependencies (via the `kubernetes` package), and `urllib3` is already a direct
   dependency used for transport-error classification in the Kubernetes collector —
   reusing one of these rather than adding a new HTTP dependency should be evaluated
   first, consistent with the project's "avoid unnecessary dependencies" rule.
3. **Checks and JSON/HTML report integration.** Unlike the Kubernetes checks, which
   fan out per-container across many pods/deployments, most of the eleven checks above
   are single-object project-settings checks (one `GET /projects/:id`-shaped read per
   check, not an iteration over many resources) — the per-check architecture may end
   up simpler than the Kubernetes container-check fan-out, but this should be
   confirmed once real API responses are being handled.
4. **Automated tests, controlled GitLab acceptance testing, documentation, and
   release preparation.**

## G. Acceptance principles

- Tests must not contact a live GitLab server.
- Mock representative HTTP responses at the API boundary — following the same
  philosophy as `tests/fixtures/builders.py`, which builds real `kubernetes.client`
  model objects rather than hand-rolled dicts; the GitLab equivalent should mock
  realistic API response payloads, not simplified stand-ins.
- Every check requires positive, negative, boundary, and missing-field tests where
  applicable (missing-field tests matter especially here given the edition/version
  API concerns noted per-check above).
- GitLab.com and self-managed base URLs must both be supported safely.
- Minimum usable token scope and minimum project role must be **proven through
  controlled live testing**, not assumed — mirrors how v0.1.0's RBAC permissions were
  validated against a real `kind` cluster rather than inferred from documentation
  alone.
- Authentication failures, forbidden responses, rate limits, invalid JSON, timeouts,
  TLS/network failures, and pagination must all eventually fail cleanly (non-zero
  exit, sanitized message, no traceback) — mirrors the existing `CollectorError`
  posture in `src/cloudops_guard/collectors/kubernetes.py`.
- Existing Kubernetes tests and behaviour must remain unchanged throughout.

## Open questions to resolve before implementation begins

These are flagged here rather than decided, since this document is scope and design
reference only:

1. **Raw/merged CI YAML tension** (`GL-CI-001`, `GL-COST-002`): determining effective
   image tags and per-job Git depth overrides likely requires reading
   `.gitlab-ci.yml` content (directly, or via the CI Lint API) at least transiently.
   §D requires this to happen in memory only, retaining nothing raw — the exact
   mechanism (which endpoint, what gets discarded immediately vs. normalized and
   kept) needs to be designed before phase 2/3 implementation, not assumed.
2. **API field verification for `GL-SEC-002` and `GL-SEC-003`**: these touch some of
   the least stable, most recently evolved parts of the GitLab REST API. Exact field
   names and edition/version availability must be confirmed against the target
   GitLab version(s) before implementation, not assumed from this document.
3. **`GL-BR-002` CE vs. EE field availability**: `allow_force_push` and similar
   EE-gated fields may be entirely absent on CE — needs a defined "unknown, not
   applicable" outcome distinct from both "protected" and "not protected."
4. **`GL-BR-003` scope**: role-based push access only, or also user/group-specific
   grants (EE)? This document scopes it to role-based only; revisit if that proves
   insufficient in practice.
5. **`GL-MR-001` when no CI config exists**: is "pipelines must succeed" a meaningful
   finding for a project with no `.gitlab-ci.yml`? Needs a decision — suppress, soften,
   or report as-is with clarifying evidence.
6. **Minimum supported GitLab version/edition**: several checks depend on
   settings/fields introduced at different points across GitLab's history. A concrete
   minimum-version target should be picked before implementation so "known
   edition/version/API-availability concerns" above can be resolved definitively
   rather than left open.
7. **Pagination**: most of these checks read single-object settings endpoints
   (`GET /projects/:id` and similar), but `protected_branches` is a list endpoint and
   may be paginated for projects with many branch-protection rules — pagination
   handling needs to be designed, not assumed to fit on one page.
8. **`--project` path encoding**: the GitLab API's `:id` parameter accepts either a
   numeric ID or a URL-encoded path (`/` → `%2F`); the CLI must handle both forms
   correctly, including projects nested under subgroups.
