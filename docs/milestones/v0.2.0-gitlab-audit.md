# Milestone v0.2.0: GitLab CI/CD Audit MVP

Status: **implementation and controlled acceptance testing complete for the
documented v0.2.0 scope; release-candidate preparation complete; not yet tagged or
released.** This document is a design and scope reference for implementation. The additive GitLab models, the HTTP client foundation, the
normalized project/protected-branch collector, the protected-default-branch checks
(`GL-BR-001` through `GL-BR-003`), the project-setting checks (`GL-MR-001`,
`GL-SEC-001` through `GL-SEC-003`, `GL-COST-001`, `GL-COST-002`), the job timeout
check (`GL-REL-001`), the separate CI Lint collection/normalization together with
`GL-CI-001`, the combined GitLab evaluator and `GitLabAuditReport` construction
(`evaluate_gitlab`, Phase 2D-A — see "Combined GitLab evaluator" below), GitLab
JSON/HTML report-file rendering (`generate_gitlab_reports`, Phase 2D-B — see "GitLab
report-file rendering" below), and end-to-end CLI integration (`cloudops-guard audit
gitlab`, Phase 2E-A — see "GitLab CLI integration" below) are implemented. Kubernetes
report generation (`generate_reports`, `report.html.j2`) and the Kubernetes CLI
command remain a separate, unchanged contract. Controlled acceptance testing has
passed on both GitLab.com's current hosted version and self-managed GitLab CE
18.4.6, at Owner and at Maintainer — on GitLab.com via a Maintainer-role project
service account, and on self-managed via an ordinary, non-service-account internal
user account (see "Controlled GitLab.com acceptance record" and "Controlled
self-managed GitLab CE 18.4.6 acceptance record" below) — **the documented minimum
required role is now Maintainer, not Owner**. Other self-managed GitLab
releases/editions and the other explicitly listed untested account/token
combinations (see "Matters requiring controlled acceptance testing" below) remain
outstanding for future evidence-broadening, but do not block this milestone's
documented scope. Release-candidate preparation — version bump to `0.2.0`, README
and documentation updates, and packaging/build validation — is **complete**. Remote
CI (GitHub Actions) passed on commit `ac75c487b6c633c758b09f71a38b198357688edb`,
the **pre-release-preparation baseline** — that commit does not include the
release-preparation changes, so it does not validate them. The release-preparation
commit must itself pass remote GitHub Actions before v0.2.0 is tagged. **Tagging
`v0.2.0` and publishing a GitHub Release remain outstanding** and are not claimed to
have happened yet.

Predecessor: v0.1.0, the Kubernetes audit MVP, released and tagged. See
[`CLAUDE.md`](../../CLAUDE.md) for durable, cross-milestone project rules (scope

GitLab-specific detail on top of those rules, it does not replace them.

## A. Objective

A read-only CLI audit of a single GitLab project, on GitLab.com or a compatible
self-managed GitLab instance. It produces `report.json` and `report.html` consistent
with CloudOps Guard's existing reporting approach (see `src/cloudops_guard/reports/`):
atomic UTF-8 writes, a static dependency-free HTML report, and a JSON report suitable
for programmatic comparison.

## B. Command interface — **implemented** (Phase 2E-A)

```bash
cloudops-guard audit gitlab \
  --gitlab-url <url> \
  --project <numeric-id-or-full-path> \
  --job-timeout-threshold-seconds <positive-integer> \
  --output <directory>
```

All four options are required; there is no `--token`, `--config`, `--insecure`,
TLS-skip, namespace/group-wide-scope, remediation/write, pipeline-simulation, or
CI-variables/jobs/logs/traces/artifacts/repository option.

- `--gitlab-url`: base URL of the GitLab instance (e.g. `https://gitlab.com` or a
  self-managed instance's base URL). Validated and normalized through the existing
  public `normalize_gitlab_base_url` before any credential or network access —
  `/api/v4` suffixes and trailing slashes are handled correctly, and an invalid URL
  is rejected before the token is ever read. Required.
- `--project`: the target project. Accepts a numeric project ID, a human-readable
  full path such as `group/subgroup/project`, or an already URL-encoded path (for
  compatibility with copy-pasted values). Validated and canonicalized through the
  existing public `canonicalize_gitlab_project` before any credential or network
  access — this matters because `GitLabCollector.collect_project_snapshot` itself
  only canonicalizes the project identifier immediately before its *second* request
  (`GET /projects/:id`), after the first (`GET /metadata`) has already fired; without
  this CLI-level pre-validation, a malformed `--project` value would only be caught
  after a live network request had already been made. Double-encoding an
  already-encoded input is prevented; empty or otherwise malformed identifiers are
  rejected; subgroup-nested projects are supported. Required.
- `--job-timeout-threshold-seconds`: the `GL-REL-001` threshold, forwarded to
  `evaluate_gitlab`/`evaluate_job_timeout_check` exactly as supplied. Required, with
  no product-level default (v0.2.0 does not guess one) — enforced as an integer
  greater than zero via Typer/Click range validation (`min=1`), so zero, negative,
  non-integer, and omitted values are all rejected before the token is read, before a
  client is constructed, before any collection occurs, and before any output file is
  created. Not added to the Kubernetes `AuditConfig` or its YAML `--config` file.
- `--output`: directory to write `report.json` and `report.html` into (via
  `generate_gitlab_reports`, see "GitLab report-file rendering" above), matching the
  existing `audit kubernetes` convention. Required.

The access token is read **only** from the environment variable
`CLOUDOPS_GUARD_GITLAB_TOKEN`, via the existing public `load_gitlab_token`. It is
never accepted as a `--token`-style CLI option and never read from a `--config` YAML
file — both would risk the token appearing in shell history, process listings, or a
committed config file. This mirrors and extends the existing credential-handling
posture: v0.1.0 already never accepts kubeconfig credentials as CLI input and never
prints them, even in exceptions. A missing or blank token exits with a sanitized
setup message before any network request or output file.

Exactly one `GitLabClient` and one `GitLabCollector` are constructed. Collection is
exactly two calls, in order: `collector.collect_project_snapshot(canonical_project)`,
then `collector.collect_ci_config_snapshot(project_snapshot)` — passing the *exact*
`GitLabProjectSnapshot` object the first call returned, never a separately
re-supplied project path/ID/branch, and never triggering an additional
metadata/project/protected-branch request. A single timezone-aware UTC timestamp
(`datetime.now(datetime.UTC)`, called exactly once) becomes `audited_at` for the one
`evaluate_gitlab` call and, transitively, `generated_at` on the resulting report and
`audited_at` on every finding. Every stage — input validation, token/client setup,
collection, evaluation, report writing — fails closed with exit code 1, a sanitized,
fixed-prefix message, and no traceback. A successfully completed audit exits 0
regardless of how many findings it produced — findings never change the exit code.

**Failure and report-file behavior, precisely**: input-validation, setup, collection,
and evaluation failures all occur *before* `generate_gitlab_reports` is ever called,
so none of them create a new report file. Report generation itself
(`generate_gitlab_reports`, see "GitLab report-file rendering" above) writes
`report.json` and then `report.html`, each via the existing atomic
write-to-temp-file-then-rename mechanism. If output-directory creation or the
`report.json` write fails, no file from the current run has been installed. If
`report.json` succeeds but the `report.html` write then fails, the new `report.json`
remains installed, while `report.html` is either absent (if this is the first run) or
retains its previous complete content from an earlier run — never a partial or
truncated file. Failed report generation can therefore leave **zero or one** newly
installed file from the current run, never two; and any pre-existing complete report
file(s) from a previous run may remain in the output directory alongside whatever the
current run did or did not install. Individual targets are never left truncated, and
a leftover temp file from a failed write is cleaned up. The two files are **not**
written as a single transaction. In every case the CLI still exits 1 with the
existing sanitized `Failed to write report to <output>: <error>` message and no
traceback. This milestone does not redesign `generate_gitlab_reports` into a
transactional pair, and does not add cleanup logic that could delete or overwrite a
previously valid report file.

Not out of scope by omission: whether to also support `--namespace`-style scoping
(GitLab "namespace" means something different from Kubernetes namespace — a
user/group namespace that *owns* a project) remains out of scope for v0.2.0 per §E;
this command audits exactly one project.

## Supported GitLab versions

- **Provisional minimum supported self-managed GitLab version: 18.4.** Chosen because
  `ci_push_repository_for_job_token_allowed` (used by `GL-SEC-002`, see §C) existed
  earlier behind a feature flag but only became generally available in GitLab 18.4 —
  an earlier minimum would make that check's required field unreliably present.
- **GitLab.com** is treated as its current hosted version at all times; no separate
  minimum-version boundary applies there.
- Self-managed instances older than 18.4 are **outside the v0.2.0 support boundary**.
  CloudOps Guard is not required to produce a correct or complete report against them.
- Implementation must verify the instance's version and the presence of required
  capabilities before relying on them. On a supported instance (18.4+, or GitLab.com),
  a field this milestone's checks require that is unexpectedly missing from a response
  must produce a sanitized "unsupported capability" failure. CloudOps Guard must never
  assume a safe default value for a missing required field (for example, treating a
  missing `allow_force_push` as `false`) — see §D and the per-check "Edition/version/
  API concerns" notes below for where this applies.

## Authentication and minimum access

This is the complete access contract a v0.2.0 audit run requires:

- **Token scope: `read_api` only.** The token must not require, and should not be
  granted, the broader `api` scope — `read_api` is sufficient for every check planned
  in this milestone, and `api` would grant write access CloudOps Guard never needs.
- **Token source: `CLOUDOPS_GUARD_GITLAB_TOKEN` only** (see above) — never a CLI
  option, never a configuration-file value.
- **Effective project role: Maintainer.** Confirmed through controlled live
  acceptance testing (2026-08-18) on **both** GitLab.com's current hosted version
  and self-managed **GitLab Community Edition 18.4.6**, using two different account
  configurations: on GitLab.com, a Maintainer-role **project service account**; on
  self-managed, an ordinary, **non-service-account** internal user account with
  direct project Maintainer access. Both completed a full audit successfully,
  returning every project field this milestone's checks require, correctly typed
  (see "Controlled GitLab.com acceptance record" and "Controlled self-managed
  GitLab CE 18.4.6 acceptance record" below). The evidence that Maintainer's
  results match Owner's differs in precision by platform: on GitLab.com, the
  Owner and Maintainer audits produced the same summary and the same finding
  order; on self-managed GitLab CE 18.4.6, the Owner and Maintainer `report.json`
  outputs were compared directly and were identical after removing only the
  `generated_at` field and each finding's `audited_at` field. **Owner remains
  sufficient** — it was tested successfully in both environments too, and
  continues to work — but Owner is **no longer the documented minimum**.

  **History**: GitLab's public API documentation states these fields — including
  `ci_default_git_depth`, `auto_cancel_pending_pipelines`, and `build_timeout` — as
  visible only to a project Owner or an instance administrator. The Phase 2C-D1
  investigation found GitLab 18.4's own source (`lib/api/entities/project.rb`,
  gated by the `:admin_project` ability; that ability is granted by
  `app/policies/project_policy.rb`'s `rule { maintainer }.enable :maintainer_access`
  before being escalated to `:admin_project`) suggested this documented restriction
  might not hold in practice, but this document intentionally kept the stated
  requirement at Owner until confirmed through controlled live acceptance testing
  — CloudOps Guard does not lower a stated access requirement on the basis of
  source-reading alone. That confirmation has now happened on two independent
  GitLab deployments (see above), so the documented minimum is lowered accordingly.
  A missing required field on an unsupported combination remains a hard
  capability/access failure, never a silently-assumed safe default (see "Supported
  GitLab versions" above and §D).

  **Bounded**: this is confirmed only for the specific configurations actually
  tested. On GitLab.com, this used a Maintainer-role *project service account*,
  not an ordinary or human-operated account. On self-managed GitLab, this used two
  ordinary, non-service-account internal accounts — active, non-admin,
  non-external, and non-bot — on specifically GitLab **Community Edition 18.4.6**;
  this establishes that ordinary (non-service-account) accounts work on that
  self-managed instance, but does not itself establish that the operators of
  those two accounts were separate human individuals. It does **not** establish
  Maintainer as sufficient for every self-managed GitLab release or version,
  GitLab Enterprise Edition or its Premium/Ultimate tiers, a human-operated
  Maintainer account on GitLab.com, or any account/token type other than a legacy
  personal access token — see "Matters requiring controlled acceptance testing"
  below for the exact remaining scope.
- **Token type**: only a legacy personal access token has been tested, at both
  Owner and Maintainer roles, on both tested GitLab deployments (see the two
  acceptance records below). Project access tokens, group access tokens, OAuth
  tokens, fine-grained personal access tokens, and administrator tokens remain
  unverified — this document does not promise support for any of them until
  verified. See "Matters requiring controlled acceptance testing" below.

Every acceptance audit performed so far — on GitLab.com and on self-managed GitLab
CE 18.4.6, at both Owner and Maintainer — used a `read_api`-scoped legacy personal
access token, and none of them issued a write request. This confirms `read_api` is
**sufficient** for every read operation the audit performs, but it does **not**
independently confirm that `read_api` actually **rejects** a write operation, since
no acceptance run ever attempted one. `read_api` therefore remains the required and
tested least-privilege scope for the audit's read operations. CloudOps Guard must
fail clearly (non-zero exit, sanitized message) if a comprehensive audit cannot
access every field it requires — it must never issue a partial report that looks
clean because some checks were silently skipped for lack of access.

## C. Agreed initial checks

Severities below are **provisional** and should be revisited once real-world evidence
(false-positive rate, operator feedback) is available, consistent with how v0.1.0's
Kubernetes check severities were assigned by judgment rather than an external standard.

Check IDs follow the existing `<PLATFORM>-<CATEGORY>-<NNN>` convention established by
the Kubernetes checks (`K8S-RES-001`, `K8S-IMG-001`, `K8S-REL-001`, ...). Once
implemented, these IDs are stable per the project's durable rules and must not change.

---

#### Protected-branch evaluation model (applies to GL-BR-001 – GL-BR-003)

All three checks below share one evaluation model, corrected from an earlier version
of this document that assumed a single matching protected-branch record:

- Retrieve **every page** of `GET /projects/:id/protected_branches` (see "HTTP client
  requirements" below for pagination handling generally) — a project can have many
  protected-branch rules.
- The response can include exact-name rules, wildcard-pattern rules (e.g. `release/*`),
  and rules **inherited from a group** (indicated by an `inherited` field on
  Premium/Ultimate) — all are in scope and must be included when determining which
  rules apply to the default branch.
- Determine **every** rule (exact, wildcard, or inherited) whose name pattern matches
  the project's actual default branch name (`default_branch` from `GET
  /projects/:id`).
- When more than one rule matches, resolve the effective result using GitLab's
  documented protected-branch rule behavior: **the most permissive matching rule
  controls** push and force-push access. (The precise mechanics of this resolution
  should be validated against a real multi-rule project — see "Matters requiring
  controlled acceptance testing" below.)
- This model deliberately does not evaluate a separate, unrelated EE feature —
  **group-level Push Rules** — which is a different mechanism from protected-branch
  inheritance and remains out of scope for v0.2.0.

### GL-BR-001 — Default branch is not protected

- **Condition**: no exact, wildcard, or inherited rule (per the evaluation model
  above) matches the project's default branch.
- **Provisional severity**: High.
- **Why it matters**: an unprotected default branch permits force-push, deletion, and
  unreviewed direct pushes by anyone with push access. The default branch is typically
  the deployment/release source of truth.
- **Evidence (non-sensitive)**: project path, default branch name, and the fact that no
  rule of any kind matched. No commit content, no member names.
- **Recommendation**: create a protected-branch rule for the default branch with
  push/merge access restricted appropriately.
- **Edition/version/API concerns**: the Protected Branches API and the core
  push/merge access-level fields are available on Free, Premium, and Ultimate — this
  is **not** an EE-only feature, correcting an earlier version of this document. The
  `inherited` indicator and granular per-user/per-group access-level fields do have
  tier-specific availability. The response shape has grown over time — the client
  must tolerate additional/missing non-required fields rather than assume a fixed
  schema, while still treating a *required* field's absence on a supported version as
  a capability/access failure (see "Supported GitLab versions" above).
- **Possible false positives**: none expected now that inherited group rules are
  explicitly in scope; a separate, unrelated EE feature (group-level Push Rules) could
  still provide protection this check does not inspect — a documented, known
  limitation, not silently corrected for.

### GL-BR-002 — Force-push is allowed on the default branch

- **Condition**: any effective rule matching the default branch (per the evaluation
  model above) permits force-push, i.e. its `allow_force_push` field is `true`. Per
  the most-permissive-wins resolution, this is a finding even if another matching
  rule sets `allow_force_push` to `false`.
- **Provisional severity**: High.
- **Why it matters**: force-push on the default branch can rewrite or destroy commit
  history, obscure prior changes, and break collaborators relying on that history —
  undermining any audit trail.
- **Evidence**: branch name and the resolved effective boolean value only.
- **Recommendation**: disable "Allowed to force push" on every rule matching the
  default branch.
- **Edition/version/API concerns**: `allow_force_push` is available on Free,
  Premium, and Ultimate — correcting an earlier version of this document that
  described it as EE-only. On a supported version (18.4+, or GitLab.com), a
  **missing** `allow_force_push` field on a rule that otherwise matches the default
  branch must be treated as malformed or unsupported API data — a capability/access
  failure (see §D) — never as "not applicable" or an implicit safe value.
- **Possible false positives**: none expected from the boolean check itself once a
  matching rule is found; the most-permissive-wins resolution across multiple
  matching rules should be validated against a real multi-rule project before
  implementation is considered complete (see "Matters requiring controlled acceptance
  testing" below).

### GL-BR-003 — Developers can push directly to the default branch

- **Condition**: any effective rule matching the default branch (per the evaluation
  model above) includes the role-based "Developer" access level (30) among its push
  access levels, rather than being restricted to Maintainer (40) or "No one."
- **Provisional severity**: Medium.
- **Why it matters**: allowing direct pushes at the Developer role bypasses merge
  request review for a broad set of contributors, reducing change visibility.
- **Evidence**: the resolved minimum role-based push access level (name/number) across
  matching rules. Never the list of specific users or groups holding that access —
  only the role threshold itself.
- **Recommendation**: restrict default-branch push access to Maintainer or "No one,"
  and require changes via merge request.
- **Scope note**: this check remains **explicitly limited to Developer role-based
  push access** for v0.2.0. Its title and evidence must not imply that user-specific,
  group-specific, deploy-key-specific, or custom-role-specific access grants
  (available on Premium/Ultimate) were evaluated — they are not, and this is a known,
  documented gap, not an oversight.
- **Edition/version/API concerns**: Premium/Ultimate allow `push_access_levels`
  entries scoped to specific users, groups, or deploy keys, and (on later versions)
  custom roles — none of these are evaluated by this check, only the role-based
  Developer-level entry.
- **Possible false positives**: the permission being *granted* does not mean it is
  ever *used* — a project may have no members actually holding the Developer role.
  The check reports the grant, not observed usage; this should be reflected in the
  finding's wording during implementation so it isn't read as "a developer pushed
  directly."

### GL-MR-001 — Successful pipelines are not required before merge

- **Condition**: the project setting `only_allow_merge_if_pipeline_succeeds` is
  `false`. This check is **always evaluated and reported when disabled — it is not
  suppressed merely because the default branch has no CI configuration.** A project
  with no `.gitlab-ci.yml` and this setting disabled is not treated as safer than a
  project with CI and the setting disabled; silently exempting "no CI" projects would
  do exactly that.
- **Provisional severity**: Medium.
- **Why it matters**: without this gate, merge requests can be merged despite failing
  CI, undermining the purpose of any configured tests, builds, or security scans.
- **Evidence**: the boolean setting value and project path. No pipeline or job data.
  When no valid CI configuration exists for the project, the evidence/remediation text
  should clarify that this pipeline gate becomes protective only once CI is
  configured — informative context, not a reason to omit or soften the finding itself.
- **Recommendation**: enable "Pipelines must succeed" in merge request settings.
- **Edition/version/API concerns**: the related setting
  `allow_merge_on_skipped_pipeline` weakens this guarantee if enabled (a skipped
  pipeline counts as "succeeded"). For v0.2.0 this remains a **documented related
  limitation**, deliberately not folded into `GL-MR-001`'s condition — a project could
  pass this check while `allow_merge_on_skipped_pipeline` still allows an effectively
  ungated merge. Combining the two into one condition, or adding a second check, is a
  decision left for a later milestone unless evidence from real use justifies it
  sooner.
- **Possible false positives**: none from the setting itself; see "Edition/version/API
  concerns" above for the related, deliberately-unaddressed skipped-pipeline gap.

### GL-CI-001 — CI job or service container image uses a mutable tag or no tag — **implemented**

- **Condition**: mirrors the existing Kubernetes `K8S-IMG-001` check, reusing its
  `_image_tag` / `_is_pinned_by_digest` helpers directly from
  `src/cloudops_guard/checks/kubernetes.py` (imported, not duplicated, so both checks
  share one source of truth for Docker image-reference parsing): a resolved job or
  service `image:` reference has no tag, or uses a known-mutable tag such as `latest`,
  and is not pinned by digest. A dynamic (CI/CD-variable-containing) reference is
  reported separately as unverifiable (see below) rather than classified as pinned or
  mutable.
- **Severity**: High (matches `K8S-IMG-001` for product consistency).
- **Why it matters**: identical rationale to `K8S-IMG-001` — reproducibility, rollback
  safety, and supply-chain traceability, arguably sharper for CI images since they
  execute with pipeline (and potentially job-token) permissions.
- **Design (resolved, corrected by the Phase 2C-E1 investigation)**: use the read-only
  **CI Lint API**, `GET /projects/:id/ci/lint`, with `content_ref` set to the
  project's normalized default branch, `dry_run=false`, and **`include_jobs=false`**
  — this is *static validation* of the existing pipeline configuration, not simulated
  pipeline creation. An earlier version of this document assumed `include_jobs=true`
  was needed for a per-job image/services breakdown; the Phase 2C-E1 investigation
  traced GitLab 18.4's own REST entity, JSON schema, and GraphQL type for the `jobs`
  array (both on `18-4-stable-ee` and current master) and found none of them expose a
  job's effective `image` or `services` at all, regardless of `include_jobs` — that
  breakdown covers job existence, stage, and `when`/`only`/`except`, not container
  images. `include_jobs=true` is therefore never enabled: it adds no image-relevant
  data and only broadens the response. Instead, the **`merged_yaml`** field — GitLab's
  fully `include:`/`extends:`/`!reference`-resolved pipeline YAML, built by
  `Gitlab::Ci::Config` before per-job entry composition — is the sole source parsed,
  client-side, via the existing PyYAML dependency (`yaml.safe_load`).
- **Project-identity binding (Phase 2C-E2 review follow-up)**:
  `GitLabCollector.collect_ci_config_snapshot` takes the already-collected
  `GitLabProjectSnapshot` itself (typically from a prior `collect_project_snapshot()`
  call on the same client), not independent `project`/`project_path`/`default_branch`
  values — the numeric project ID, project path, and default branch used for the CI
  Lint request are all derived exclusively from that snapshot, so a caller cannot
  substitute a different project path or branch than the one actually collected.
  Before issuing the request, the method also requires
  `project_snapshot.gitlab_url == client.instance_base_url`, raising a fixed,
  sanitized error before any HTTP request if they differ — guarding against
  evaluating a snapshot collected from one GitLab instance against a client
  configured for a different one.
- **Narrow, bounded normalization (not a CI compiler)**: CloudOps Guard does not
  reimplement GitLab's pipeline compiler. GitLab has already resolved `include:`,
  `extends:` (including chained/multi-parent), and `!reference` server-side by the
  time `merged_yaml` is returned — and only those three constructs; `merged_yaml` is
  **not** a fully evaluated pipeline. GitLab's CI Lint does not resolve CI/CD variable
  values or evaluate `rules:`/`workflow:` conditions — a reference such as `$TAG`
  still appears literally in `merged_yaml` exactly as authored. CloudOps Guard's own
  normalization narrowly resolves only effective job/service *image* inheritance
  across the proven precedence order: a job's own `image:`/`services:` always wins;
  otherwise `inherit: {default: ...}` (boolean or per-key list, defaulting to inherit)
  selects whether the job receives `default:` (or, if `default:` is absent, the
  deprecated legacy top-level `image:`/`services:`) — an explicit `services: []` on a
  job is a deliberate override that suppresses inherited services, not "no override."
  Hidden/template entries (name starting with `.`) and trigger bridges (`trigger:`
  present, no `script:`/`run:`) never resolve an image. A needs-only entry (`needs:`
  present, no `trigger:`/`script:`/`run:`) is skipped only when its `needs:` value is
  the source-proven `needs:pipeline` bridge shape, in **either** of the two forms
  GitLab itself accepts identically: the documented bare mapping
  (`needs: {pipeline: <value>}`, per GitLab's own CI/CD YAML reference example) or a
  single-element list containing that same mapping (`needs: [{pipeline: <value>}]`) —
  both reach GitLab's `Entry::Need` as the same single Hash, since `Entry::Needs`
  (`ComposableArray#compose!`) wraps a bare `Hash` `needs:` value into a one-element
  array (`[@config].flatten`, which does not recurse into a `Hash`) before per-item
  classification. Traced to GitLab EE's `Entry::Need` prepend
  (`ee/lib/ee/gitlab/ci/config/entry/need.rb`, `BridgeHash` strategy — confirmed
  identical on `18-4-stable-ee` and current master; this specific bridge form is an
  EE-only strategy), the mapping must contain **exactly** the single key `pipeline`,
  with a non-empty string value — GitLab validates only `pipeline`'s type, never its
  content, so a CI/CD variable reference such as `$UPSTREAM_PROJECT` is itself a valid
  non-empty string and is accepted, without CloudOps Guard retaining or reproducing it
  anywhere (a bridge is always skipped entirely, never partially represented). A `job`
  or `project` key present instead routes GitLab to a different, non-bridge
  classification. `needs: []`, job-only needs (in either mapping or list form), a
  scalar `needs:` value, multiple pipeline entries, a `pipeline:`+`job:`
  cross-dependency entry, an empty mapping, or a mapping carrying any key besides
  `pipeline` all fail closed rather than being silently treated as an ignorable bridge
  (see "Malformed `valid: true` response hardening" below). Variables, `rules:`, and
  any other pipeline
  semantics are never evaluated by CloudOps Guard either — an image/service value
  containing an unresolved variable reference is converted to a generic
  dynamic/unverifiable marker (see "Dynamic image references" below) rather than
  resolved or guessed at. A `valid: false` CI Lint result — including one caused by a
  legacy-top-level-vs-`default:` conflict — is always a fixed, sanitized collection
  failure; GitLab's specific `errors`/`warnings` content is never inspected,
  reproduced, or used to select special-case handling or a repair attempt.
- **Malformed `valid: true` response hardening (Phase 2C-E2 review follow-up)**: a
  `valid: true` result is normally guaranteed well-formed by GitLab's own validation,
  but normalization does not fully trust that guarantee for structures relevant to
  image resolution. `inherit:default:[...]` list members are validated to be plain
  strings (never `bool`, `int`, `null`, a mapping, or a nested list) drawn from
  GitLab's documented, closed `default:` keyword set (`after_script`, `artifacts`,
  `before_script`, `cache`, `hooks`, `id_tokens`, `image`, `interruptible`, `retry`,
  `services`, `tags`, `timeout`) — an unrecognized member fails closed without being
  reproduced in the error. A needs-only entry's `needs:` shape is validated against
  the narrow `needs:pipeline` bridge form described above before being treated as
  ignorable, rather than any `needs:`-bearing entry being assumed safe to skip. Any
  Pydantic `ValidationError` that untrusted merged-YAML content could still trigger at
  model-construction time (for example an empty string used as a YAML mapping key,
  rejected by `GitLabCiImageReference`'s `job_name` `min_length=1`) is caught at the
  normalization boundary and replaced with the same fixed, sanitized
  unsupported-structure error — Pydantic's own `input_value`/field/message detail,
  which could quote untrusted content, never escapes directly.
  A merged-YAML structure this narrow algorithm does not recognize as one of the above
  cases is itself a fixed, sanitized normalization failure — never silently treated as
  "no image."
- **Evidence**: job name, whether the reference is a job image or a service image, and
  the resolved static image reference with its tag noted — never job scripts, never
  variable values, never includes, never the raw or merged CI Lint response.
- **Recommendation**: pin to a specific version tag at minimum; pin to a digest for
  the strongest guarantee — reusing the same wording pattern as `K8S-IMG-001`.
- **Privacy and sanitized-failure handling (implemented, per §D)**: the CI Lint
  response and the decoded `merged_yaml` string exist transiently in memory only, are
  never bound to a named local variable across a collection call the way the
  `GET /projects/:id` response is not (see "Raw-response minimization" in the
  collector), and are never written to disk, logs, reports, test snapshots, or
  terminal output. Only project path, job name, image resource kind (job/service), and
  either a static image string or a dynamic/unverifiable marker are retained — see
  `GitLabCiImageReference`/`GitLabCiConfigSnapshot` in `models.py`. Every CI Lint `404`
  response is treated, in this phase, as a fixed, sanitized collection failure — the
  same as GitLab's other 4xx/5xx statuses — and is **never** reinterpreted as "this
  project has no `.gitlab-ci.yml`" or used to silently report a clean audit; the 404
  response body is never inspected to make that distinction. Distinguishing a
  genuinely-absent CI configuration from an access/routing 404 remains a possible,
  optional future usability refinement — not resolved here, and not to be inferred
  from untrusted response text (see "Matters requiring controlled acceptance testing"
  below).
- **Dynamic image references**: an image reference containing a CI/CD variable (e.g.
  `image: $CI_REGISTRY_IMAGE:$TAG` or `${CI_REGISTRY_IMAGE}`) is never resolved — this
  tool never evaluates variable values. Such a reference is reported under `GL-CI-001`
  as an unverifiable image reference that could not be statically checked, using fixed
  generic wording; the variable name, the raw expression text, and any part of the
  original image string containing it are never retained in the normalized model or
  reproduced in the finding.
- **Possible false positives**: `include:`-based external CI config from another
  project is resolved by the CI Lint API itself (see "Design" above), so this is
  handled rather than an open scoping question. Dynamic references (above) are
  reported as unverifiable rather than guessed at, which is a known, intentional
  under-reporting for those specific jobs, not a false negative to "fix" by guessing.

### GL-SEC-001 — CI/CD pipeline details have broad visibility

- **Condition**: project `visibility` is `private` or `internal`, and `public_jobs`
  (the "Public pipelines" setting) is `true`.
- **Provisional severity**: High.
- **Why it matters** (corrected from an earlier version of this document that
  described this as making the project's pipelines "public"): per GitLab's
  documentation, this setting never exposes a private or internal project's
  pipelines to unauthenticated outsiders — but the audience it does expose them
  to differs by visibility, and is **not** uniformly "project members only":
  - For a `private` project, pipeline details become visible to all project
    members, including Guests, but **not** to non-project members.
  - For an `internal` project, pipeline details become visible to any
    authenticated, non-external instance user — this **does** include
    non-project members, unlike `private`.

  With this setting enabled, pipeline logs, artifacts, and pipeline security
  scan information may be visible to a broader audience than intended for the
  project's visibility level. Enabling this does not prove anyone has actually
  viewed that information — it changes what is possible, not what occurred.
  Broad visibility may also be an intentional, approved choice for the
  project, making this a possible false positive rather than a certain
  defect. This check itself never fetches pipeline, job log, artifact, or
  security scan content — it evaluates the configuration only.
- **Evidence**: project visibility level and the resolved audience the setting
  exposes pipeline details to, worded per visibility as described above (never a
  blanket "public" claim, never a blanket "members only" claim, and never a user
  or member identity).
- **Recommendation**: disable project-based pipeline visibility unless the broader
  audience is deliberate and approved.
- **Edition/version/API concerns**: a self-managed instance may have its own
  `restricted_visibility_levels` policy that changes what `internal` effectively
  means instance-wide. This check's notion of visibility is explicitly scoped to
  the project-level `public_jobs`/`visibility` fields only, not instance-wide
  policy.
- **Possible false positives**: broad pipeline visibility may be an intentional,
  approved choice (e.g. an internal project that wants pipeline transparency
  across the organization) — this check reports the configuration, not a
  confirmed problem.

### GL-SEC-002 — CI job tokens are permitted to push to the repository

- **Condition**: the project (Projects API) field `ci_push_repository_for_job_token_allowed`
  is `true`. Treat `true` as a finding and `false` as passing.
- **Provisional severity**: High.
- **Why it matters**: the job token is an ambient credential available to every
  pipeline job. If it can push to the repository, a compromised or malicious job (for
  example, from a dependency compromise or a pipeline triggered by an untrusted merge
  request) gains a repository-write escalation path.
- **Evidence**: the `ci_push_repository_for_job_token_allowed` boolean value only.
- **Recommendation**: disable `ci_push_repository_for_job_token_allowed` unless a
  specific, reviewed automation depends on job-token repository push access.
- **Edition/version/API concerns**: `ci_push_repository_for_job_token_allowed` existed
  earlier behind a feature flag and became generally available in GitLab 18.4, the
  v0.2.0 minimum supported self-managed version (see "Supported GitLab versions"
  above). On a supported version, absence of this field is a capability/access
  failure — see §D — not an implicit `false`.
- **Possible false positives**: legitimate automation (e.g. a bot that tags releases
  from CI) may intentionally need this permission. The finding should be worded as "a
  security-relevant configuration exists," not "this is necessarily wrong."

### GL-SEC-003 — Pipeline-variable override permissions are more permissive than Maintainer

- **Condition**: the project (Projects API) field
  `ci_pipeline_variables_minimum_override_role` equals `developer`. The documented
  values for this field are `no_one_allowed`, `owner`, `maintainer`, and `developer`.
  Only `developer` is more permissive than Maintainer, so only `developer` raises this
  finding; `maintainer`, `owner`, and `no_one_allowed` all pass. An unknown value or a
  missing required field must not be treated as passing — treat it as a
  capability/access failure (see §D), never as an implicit safe value.
- **Provisional severity**: High.
- **Why it matters**: if a lower-privileged role than Maintainer can override pipeline
  variables at trigger time, it may be able to inject values into unsafely-
  interpolated scripts or override security-relevant variables — an authorization
  bypass risk.
- **Evidence**: the `ci_pipeline_variables_minimum_override_role` string value only.
  This check must never call any CI/CD variables endpoint and must never report
  variable names or values (§D).
- **Recommendation**: raise the minimum pipeline-variable override role to
  `maintainer` (or more restrictive).
- **Edition/version/API concerns**: the legacy boolean field
  `restrict_user_defined_variables` is mentioned here only as historical
  compatibility context (older GitLab versions used it to mean roughly "restrict to
  Maintainer+"); it is not the v0.2.0 field. `GL-SEC-003` uses
  `ci_pipeline_variables_minimum_override_role`, expected available on the v0.2.0
  minimum supported version (18.4+).
- **Possible false positives**: none especially notable beyond version-specific field
  drift, given the minimum-version boundary above.

### GL-COST-001 — Redundant pipelines are not automatically cancelled

- **Condition**: the project (Projects API) field `auto_cancel_pending_pipelines` is
  a **string** setting — expected values are `"enabled"` or `"disabled"`, not a
  boolean — and its value is `"disabled"`.
- **Provisional severity**: Low.
- **Why it matters**: with automatic cancellation disabled, superseded pending
  pipelines (e.g. from rapid successive pushes to the same branch/MR) may continue
  consuming runner capacity rather than being cancelled in favor of a newer run,
  and interruptible running pipelines may also continue consuming runner capacity
  and compute time instead of being stopped when superseded — a possible cost and
  runner-contention concern, not a security one, and not a claim that such
  consumption was actually observed for any specific run.
- **Evidence**: the `auto_cancel_pending_pipelines` string value.
- **Recommendation**: set `auto_cancel_pending_pipelines` to `"enabled"`
  ("Auto-cancel redundant, pending pipelines" in the UI), unless the project
  intentionally requires every pipeline to run to completion for compliance or
  audit-history purposes.
- **Edition/version/API concerns**: stable, longstanding field across CE/EE; note the
  string type above — implementation must not treat it as a boolean or coerce it with
  Python truthiness.
- **Possible false positives**: projects that intentionally want every pipeline to
  run to completion (e.g. for a complete audit/compliance run history) may disable
  this deliberately.

### GL-COST-002 — Git clone depth is unlimited — **implemented**

- **Condition**: limited in v0.2.0 to the project-level default: the normalized
  `ci_default_git_depth` project setting is exactly `0` or `null`. Both
  representations are proven (Phase 2C-D1 investigation, source-traced from GitLab
  18.4's `ProjectCiCdSetting`/`Ci::BuildRunnerPresenter` through GitLab Runner's
  `shells/abstract.go`) to be operationally identical: GitLab coerces a `null`
  default to `0` (via Ruby's `nil.to_i == 0`) before sending the effective depth to
  GitLab Runner, and Runner treats `depth <= 0` as "fetch full history, no `--depth`
  limit." A bounded positive integer (`1`-`1000`, GitLab's own validated range) never
  triggers this check. A missing key remains a capability/access failure, never an
  "unlimited" value. Values outside `0`-`1000` are treated as a malformed response by
  the collector/model layer and never reach this check as a valid state.
- **Provisional severity**: Low.
- **Why it matters**: when this project default applies, CI jobs that obtain
  repository sources may fetch full history, potentially increasing network
  transfer, checkout duration, runner usage, and compute cost — particularly for
  large or long-lived repositories. This is conditional, not observed: the
  configuration does not prove any additional cost, transfer, or delay actually
  occurred, and CloudOps Guard does not inspect pipelines, jobs, repository history,
  clone traffic, or runner usage to find out.
- **Evidence**: the configured `ci_default_git_depth` value, worded distinctly for
  `0` ("Configured project default Git clone depth: 0 (unlimited/full history)")
  versus `null` ("Configured project default Git clone depth: unset (null), which
  GitLab treats as unlimited/full history") — the evidence never claims a `null` API
  value was literally `0`.
- **Recommendation**: set a bounded positive project default Git clone depth
  appropriate to the project's branching, tagging, and history requirements.
  Unlimited history may be intentional and legitimate for work such as versioning or
  changelog generation across complete tag/history information — no single universal
  depth value is recommended.
- **Edition/version/API concerns**: `ci_default_git_depth` is gated behind the
  `:admin_project` ability in GitLab 18.4's Projects API entity — see the
  Owner-versus-Maintainer resolution in "Authentication and minimum access."
- **Possible false positives / known false negatives**: young repositories with
  little history make this setting moot; projects that specifically need full history
  in CI (e.g. changelog generation across all tags) legitimately need unlimited
  depth. Per-job/pipeline `GIT_DEPTH` variable overrides are explicitly **outside
  this check's v0.2.0 evaluation scope** — a job could override a bounded project
  default back to unlimited depth (or a bounded value even when the project default
  is unlimited) and this check would not detect it. This is a documented, accepted
  false-negative gap for v0.2.0, not an oversight; the finding's own wording states
  this limitation.

### GL-REL-001 — Project job timeout exceeds a configurable threshold

- **Condition**: the project setting `build_timeout` (seconds) exceeds an
  operator-configurable threshold, mirroring the existing `--restart-threshold`
  pattern from `audit kubernetes`.
- **Provisional severity**: Medium.
- **Why it matters**: straddles reliability and cost — an excessively long timeout
  lets a hung job occupy a runner slot for a long time before GitLab kills it,
  delaying feedback and, on paid/self-hosted runners, increasing cost.
- **Evidence**: the configured timeout (human-readable, e.g. minutes) versus the
  configured threshold. No job-specific data.
- **Recommendation**: lower the project's default job timeout to a value appropriate
  for its typical job durations; use per-job `timeout:` overrides sparingly for
  legitimately long jobs.
- **Edition/version/API concerns**: `build_timeout` is a longstanding, stable Projects
  API field — the lowest API-stability risk of the eleven checks here.
- **Possible false positives**: projects with legitimately long-running jobs (large
  builds, ML training, etc.) may need a higher timeout deliberately — this is exactly
  why the threshold must be operator-configurable rather than fixed.

### Combined GitLab evaluator — **implemented** (Phase 2D-A)

`evaluate_gitlab` in `src/cloudops_guard/engine/evaluator.py` is one pure orchestration
entry point that runs every implemented GitLab check and constructs a
`GitLabAuditReport`. It lives in the existing, shared `engine/evaluator.py` module
alongside the Kubernetes `evaluate(...)` entry point — not a separate GitLab evaluator
module — since there is no concrete architectural reason for one; the Kubernetes
`evaluate(...)` contract is unchanged.

- **Contract**:

  ```python
  def evaluate_gitlab(
      project_snapshot: GitLabProjectSnapshot,
      ci_config_snapshot: GitLabCiConfigSnapshot,
      *,
      audited_at: dt.datetime,
      job_timeout_threshold_seconds: int,
  ) -> GitLabAuditReport:
  ```

- **Pure orchestration only**: no HTTP, filesystem, environment-variable, logging, or
  subprocess access; no client, collector, token, URL, output-path, or raw-response
  argument; never mutates either snapshot; never duplicates any check's condition or
  finding wording. It delegates exclusively to the four existing public GitLab check
  entry points: `evaluate_protected_branch_checks`, `evaluate_project_setting_checks`,
  `evaluate_job_timeout_check`, `evaluate_ci_image_check`.
- **Operator-supplied threshold required**: `job_timeout_threshold_seconds` is
  forwarded to `evaluate_job_timeout_check` exactly as supplied — its existing
  validation contract (a real, non-boolean, positive `int`, or a fixed sanitized
  `ValueError`) is reused, not reimplemented, and there is still no product-level
  default (see `GL-REL-001` above).
- **Project/CI snapshot identity binding**: `project_snapshot` and `ci_config_snapshot`
  must describe the same project, checked by exact
  `ci_config_snapshot.project_path == project_snapshot.project.project_path` equality
  — a mismatch raises a fixed, sanitized `ValueError` (reproducing neither path)
  *before* any check evaluator runs. The two snapshots' `collected_at` values are
  never compared or required to match — they come from two separate, sequential
  collection operations (`collect_project_snapshot`, then
  `collect_ci_config_snapshot`) and may legitimately differ.
- **`audited_at` validation**: must be a real, timezone-aware `datetime` — a naive
  value, a non-`datetime` value, or a `datetime` whose `tzinfo` returns `None` from
  `utcoffset()` raises a fixed, sanitized `ValueError` before any check runs. The
  exact same value is then passed to every delegated evaluator and becomes the
  report's `generated_at` and every finding's `audited_at`; `datetime.now()` is never
  called here.
- **Stable combined finding order (documented contract)**: protected-branch findings,
  then project-setting findings, then the optional `GL-REL-001` timeout finding, then
  CI-image findings — preserving each delegated evaluator's own internal order
  exactly, including every per-occurrence `GL-CI-001` finding with no deduplication.
- **Report identity**: `platform="gitlab"`, `gitlab_url`, `project_id`,
  `project_path`, and `default_branch` come exclusively from `project_snapshot` (never
  from `ci_config_snapshot`). The report never carries the GitLab version, the
  enterprise flag, either snapshot's `collected_at`, a raw response, merged YAML, a
  script, a variable, a credential, a token, a warning, an error, an include, a job, a
  pipeline, a log, a trace, an artifact, or repository content.
- **Summary**: a small GitLab-specific `_summarize_gitlab` helper (mirroring the
  Kubernetes `_summarize` helper's logic, but kept separate rather than shared, since
  `Finding` and `GitLabFinding` are intentionally independent, non-inheriting models)
  counts Critical/High/Medium/Low exactly from the final combined finding list;
  `summary.total` always equals `len(findings)`.
- **Not in this phase**: JSON/HTML report-file rendering and CLI integration — see §F.

### GitLab report-file rendering — **implemented** (Phase 2D-B)

`generate_gitlab_reports` in the existing `src/cloudops_guard/reports/generator.py`
renders an already-built `GitLabAuditReport` to `<output_dir>/report.json` and
`<output_dir>/report.html`. It is a second, separate rendering path in that same
module, alongside the Kubernetes `generate_reports` — not a shared, loosely typed
`object` handler and not a broad report abstraction — and reuses only the small
platform-neutral mechanics that were already generic (`_atomic_write`,
`_environment`, `_SEVERITY_ORDER`). The Kubernetes functions, the existing
`report.html.j2` template, and the released `report.json`/`report.html` byte-for-byte
output are unchanged.

- **Contract**:

  ```python
  def generate_gitlab_reports(
      report: GitLabAuditReport,
      output_dir: Path,
  ) -> tuple[Path, Path]:
  ```

- **Operates only on the report**: takes no client, collector, token, URL, or
  evaluator argument. `GitLabAuditReport` is the sole audit-data input — no HTTP,
  environment-variable, collection, or evaluation access occurs. Filesystem/
  package-resource activity is limited to: loading the packaged GitLab HTML
  template via Jinja's `PackageLoader`; the same same-directory-temp-file-plus-
  atomic-rename writes `_atomic_write` already performs for Kubernetes reports
  (create the output directory and missing parents; replace existing report
  files; clean up a leftover temp file after a failed write; propagate
  `OSError`).
- **JSON**: `report.model_dump_json(indent=2) + "\n"` — UTF-8, a trailing newline,
  `GitLabAuditReport`'s declared field order, and `report.findings`' order preserved
  exactly (the order `evaluate_gitlab` produced — see "Combined GitLab evaluator"
  above); no wrapper, no additional metadata, and nothing beyond what
  `GitLabFinding`/`GitLabAuditReport` already declare (never a raw API response,
  merged YAML, script, variable, token, credential, warning, error, pipeline, log,
  trace, artifact, repository content, or either snapshot's `collected_at`). Always
  validates back into `GitLabAuditReport`, including for an empty findings list and a
  zero summary.
- **HTML**: a separate template, `src/cloudops_guard/reports/templates/
  gitlab_report.html.j2` (`report.html.j2` is not modified, since it is part of the
  released Kubernetes byte-for-byte contract). Dependency-free static HTML with
  inline CSS only — no JavaScript, no external fonts/images/stylesheets/CDN
  resources/trackers/network requests — rendered through the same
  `autoescape=True` Jinja environment as the Kubernetes template, so every
  displayed value (GitLab URL, project path, default branch, resource name, job
  name, evidence, etc.) is escaped and never rendered as active markup; the GitLab
  URL is shown as escaped text, deliberately never turned into a hyperlink. Severity
  summary cards and finding groups follow Critical → High → Medium → Low
  (`_SEVERITY_ORDER`), preserving each group's relative finding order exactly, as
  produced by `evaluate_gitlab`.
- **Header/identity area**: project path, GitLab instance URL, numeric project ID,
  default branch, and the generated timestamp.
- **Finding presentation**: title, check ID, severity (via section/group styling),
  resource kind (`Project`/`ProtectedBranch`/`CIJob`/`CIService`, rendered
  accurately), resource name, project path, evidence, impact, recommendation, and
  auto-remediable status; job name is shown only when non-null, so a
  `job_name=None` project/protected-branch finding never produces a blank "job"
  label. Never displays or refers to Kubernetes-only concepts (cluster context,
  namespace, pod, deployment, Kubernetes container name). A dynamic-image
  `GL-CI-001` finding displays only its existing generic, normalized `resource_name`/
  `evidence` values — the template never attempts to reconstruct or infer the
  original dynamic expression.
- **Footer**: GitLab-specific, accurately stating that CloudOps Guard performs a
  read-only audit, does not modify the GitLab project, and does not report
  credentials, tokens, raw/merged CI configuration, scripts, variable values, job
  logs, traces, or artifacts — it does not claim GitLab itself returned no sensitive
  data (the collector's documented unavoidable-field exception still applies; see
  "Approved unavoidable-field exception" above).
- **Golden fixtures**: `tests/fixtures/golden_gitlab_report.{json,html}` are the new
  GitLab report contract, generated once and reviewed, covering `Project`/
  `ProtectedBranch`/`CIJob`/`CIService` resource kinds, multiple severities, and both
  a `null` and a non-null `job_name` — mirroring
  `tests/fixtures/golden_kubernetes_report.{json,html}`'s existing role for the
  Kubernetes report. The existing Kubernetes golden fixtures are untouched.
- **Not in this phase**: CLI integration (wiring `generate_gitlab_reports` to a
  command) — implemented in Phase 2E-A, see "GitLab CLI integration" below.

### GitLab CLI integration — **implemented** (Phase 2E-A)

`cloudops-guard audit gitlab` (see §B for the full command contract) connects the
already-implemented components without duplicating their logic: it validates and
normalizes CLI input, loads the token, constructs one `GitLabClient` and one
`GitLabCollector`, collects the project snapshot and then the CI configuration
snapshot bound to it, evaluates through the one existing `evaluate_gitlab` entry
point, renders through the one existing `generate_gitlab_reports` entry point, and
prints a separate GitLab-specific summary — it never calls an individual GitLab
check, reconstructs a finding, or computes a summary itself.

- **Validation before credentials/network access**: `--gitlab-url` and `--project`
  are validated through the existing public `normalize_gitlab_base_url` and
  `canonicalize_gitlab_project` functions — never reimplemented in `cli.py` — before
  `load_gitlab_token()` is ever called. An invalid value exits 1 with a fixed
  `Invalid GitLab input:` prefix and the existing sanitized `GitLabClientError` text;
  neither the token nor a client/collector is ever touched, and no request is made.
- **Token handling**: sourced only via `load_gitlab_token()` (itself reading only
  `CLOUDOPS_GUARD_GITLAB_TOKEN`), passed to `GitLabClient` unchanged, never logged,
  printed, or included in success output, exception text, or either report. A
  missing or blank token exits 1 with a fixed `GitLab setup failed:` prefix, no
  network request, and no report files.
- **Collection**: exactly `collector.collect_project_snapshot(canonical_project)`
  then `collector.collect_ci_config_snapshot(project_snapshot)` — the second call
  receives the *exact* object the first returned, never an independently supplied
  project path/ID/branch, and the CLI issues no additional GitLab endpoint call
  itself. A `GitLabClientError` from either step exits 1 with a fixed
  `Collection failed:` prefix, sanitized, no traceback, no report files.
- **Evaluation**: one `datetime.now(datetime.UTC)` call becomes the single
  `audited_at` passed to the one `evaluate_gitlab` call — propagated to
  `generated_at` and every finding's `audited_at` — never mutating either snapshot.
  A sanitized `ValueError` from `evaluate_gitlab` (e.g. a project/CI snapshot
  identity mismatch, or an invalid threshold — the CLI does not reimplement that
  validation, only forwards the value) exits 1 with a fixed `Evaluation failed:`
  prefix and no report files.
- **Report generation**: exactly one `generate_gitlab_reports(report, output)` call
  — never the Kubernetes `generate_reports`. An `OSError` exits 1 with the existing
  `Failed to write report to <output>: <error>` style, no traceback.
- **Summary**: a separate GitLab-specific printer (the existing Kubernetes summary
  contract/text is unchanged); identity (project path, GitLab URL) comes from the
  completed `GitLabAuditReport`, never raw CLI input. A successful audit exits 0
  regardless of finding count — findings never change the exit code.
- **Kubernetes compatibility**: `audit kubernetes`'s parameters, configuration
  precedence, summary text, error prefixes, report generation, and underlying
  collector/evaluator/check logic are all unchanged; existing Kubernetes tests and
  golden fixtures are untouched.
- **Not in this phase**: controlled live GitLab acceptance testing and release
  preparation — see §F and §G.

## D. Security and privacy invariants

- Use read-only GitLab API operations only.
- Never call project, group, or instance CI/CD variables endpoints.
- Never collect or report job traces, logs, artifacts, credentials, or tokens.
- Never persist raw or merged CI YAML in reports.
- Never reproduce CI scripts or variable values in findings or error messages.
- CI configuration processed to evaluate `GL-CI-001` (see §C for the resolved design)
  is handled only in memory, retaining only the normalized, non-sensitive fields the
  check actually needs — the raw content itself is never written to a report, log, or
  intermediate file.
- Never log authentication headers.
- Sanitize remote API errors and untrusted response content before they reach a
  report or the terminal — mirrors the v0.1.0 Kubernetes collector's existing
  approach of never surfacing raw `ApiException.reason`/body/headers.
- A failure to access required information must not silently produce a partial clean
  report: if a check cannot be evaluated because required data could not be
  retrieved, the audit must fail loudly (non-zero exit) rather than omit the check and
  report as if everything else passing meant the project was clean.

These extend, and do not replace, the existing read-only invariants in
[`CLAUDE.md`](../../CLAUDE.md).

### Approved unavoidable-field exception: `GET /projects/:id`

`GET /projects/:id` is on the small allowlist of endpoints this milestone is permitted
to call (see "Permitted API operations" in the Phase 2B implementation notes below).
Several project settings this milestone's checks depend on — including
`ci_default_git_depth`, `auto_cancel_pending_pipelines`, and `build_timeout` (see
"Authentication and minimum access" above) — are documented by GitLab's public API
reference as visible in this response only to a project Owner or an instance
administrator. Controlled live acceptance testing has since qualified that
documented restriction: on **both** GitLab.com's current hosted version and
self-managed GitLab CE 18.4.6, complete audits against tested Maintainer-role
accounts each returned every one of these fields, correctly typed (see "Controlled
GitLab.com acceptance record" and "Controlled self-managed GitLab CE 18.4.6
acceptance record" below) — so the documented Owner-or-administrator restriction
does not hold universally in practice for the tested configurations, which is why
this document's stated minimum role is now Maintainer (see "Authentication and
minimum access" above) rather than Owner. Other self-managed GitLab releases and
editions remain untested, so this document does not generalize beyond the tested
configurations. For sufficiently privileged callers, this endpoint can also
include unrelated sensitive fields GitLab provides automatically, most notably
`runners_token`. (The raw Maintainer-role responses from both acceptance sessions
above, and any unrelated field within them, were not inspected — neither session
checked whether `runners_token` or any other unrelated sensitive field was
actually present in that specific response; only the explicit allowlist of
normalized fields the collector reads was verified as present and correctly
typed.) GitLab's Projects API documentation offers no field-selection or
sparse-fieldset option for this endpoint that would let CloudOps Guard request
only the fields it needs, so this is unavoidable: the sensitive fields arrive
whether or not CloudOps Guard wants them.

The project settings this milestone requires justify calling this specific, approved
endpoint despite that. The exception granted is narrow and does not weaken any other
invariant in this document or in `CLAUDE.md`:

- Only an explicit allowlist of normalized fields (see `GitLabProjectSettings` in
  `src/cloudops_guard/models.py`) may survive past the point the response is parsed.
  Every other field — `runners_token`, `owner`, `import_url`, repository clone URLs,
  descriptions, member data, and any future field GitLab adds — is read never, or read
  and immediately discarded; none of it is retained on any object, model, or snapshot.
- The raw response and any unrelated field within it are transient, existing only
  during normalization. They are never persisted, logged, printed, cached, reported,
  returned from the collector, attached to the normalized snapshot, or included in an
  exception message — even when normalization itself fails.
- This does not authorize calling credential, token, CI/CD variables,
  runner-management, job-log, trace, artifact, or repository-file endpoints — those
  remain prohibited exactly as stated elsewhere in this document and in `CLAUDE.md`.
  The exception is specific to this one approved, allowlisted endpoint whose response
  cannot be field-filtered; it is not a general license to accept sensitive fields from
  any endpoint.
- CloudOps Guard does not claim that Python can securely zeroize immutable strings or
  response buffers in memory. The guarantee made here is immediate minimization
  (normalize-then-discard, with no larger retained object referencing the raw
  response) and no persistence, reproduction, or onward transmission — not that the
  bytes are cryptographically erased from process memory.
- CI Lint response normalization (`GL-CI-001`, see §C) was a separate, later milestone
  task, out of scope for the Phase 2B collector this exception was originally written
  for; it is implemented (Phase 2C-E2) as its own entry point
  (`GitLabCollector.collect_ci_config_snapshot`), not folded into the Phase 2B
  collector above. `GET /projects/:id/ci/lint` carries no equivalent unavoidable-field
  exception of its own — see "Privacy and sanitized-failure handling" under `GL-CI-001`
  in §C.

## HTTP client requirements (pagination and transport/URL safety)

These apply to the GitLab HTTP client introduced in implementation phase 2 (§F):

- Request the maximum supported page size where the endpoint allows it.
- Follow GitLab's pagination via the `Link` response header (or the documented
  next-page mechanism for a given endpoint), rather than assuming all results fit on
  one page — relevant in particular to `GET /projects/:id/protected_branches` (see
  §C).
- Detect pagination loops and impose a defensible maximum page count, so a
  misbehaving or unexpected server response cannot cause unbounded iteration.
- Never forward the `Authorization` header (or any authentication header) to a
  different origin than the configured `--gitlab-url`.
- Do not automatically follow cross-origin redirects.
- Reject a `--gitlab-url` value that embeds credentials, a query string, or a
  fragment — the base URL must be a plain origin/path.
- Require verified TLS for remote hosts; do not add an `--insecure`/skip-verification
  option.
- Apply bounded connection and read timeouts to every request.
- Never include the token or any authentication header in exception messages,
  consistent with the existing kubeconfig-credential handling precedent (§D and
  `CLAUDE.md`).

## F. Planned implementation phases

1. **Minimal platform-neutral reporting/model adaptation**, preserving Kubernetes
   behaviour exactly. The current `Finding`/`AuditReport` models
   (`src/cloudops_guard/models.py`) are Kubernetes-shaped: `Finding.cluster_context`,
   `Finding.namespace`, `Finding.container_name`, and the closed `ResourceKind` enum
   (`Namespace` / `Pod` / `Deployment`) don't map cleanly onto a GitLab project
   (no cluster, no container; GitLab's own "namespace" concept means something
   different — the group/user that owns a project). This phase generalizes the shared
   models just enough to support a second platform without changing the existing
   `report.json`/`report.html` output for `audit kubernetes` byte-for-byte. The exact
   shape of that generalization (renaming fields vs. introducing a platform-specific
   wrapper) is an implementation-time design decision, not decided here.
2. **GitLab HTTP client, error sanitization, and normalized project snapshot.** Must
   satisfy "HTTP client requirements (pagination and transport/URL safety)" above.
   Note for implementation: `requests` and `urllib3` are already transitive
   dependencies (via the `kubernetes` package), and `urllib3` is already a direct
   dependency used for transport-error classification in the Kubernetes collector —
   reusing one of these rather than adding a new HTTP dependency should be evaluated
   first, consistent with the project's "avoid unnecessary dependencies" rule.
3. **Checks and JSON/HTML report integration.** Unlike the Kubernetes checks, which
   fan out per-container across many pods/deployments, most of the eleven checks above
   are single-object project-settings checks (one `GET /projects/:id`-shaped read per
   check, not an iteration over many resources) — the per-check architecture may end
   up simpler than the Kubernetes container-check fan-out, but this should be
   confirmed once real API responses are being handled. All eleven checks, the
   combined evaluator/`GitLabAuditReport` construction that ties them together
   (`evaluate_gitlab`, Phase 2D-A — see "Combined GitLab evaluator" above), and
   GitLab JSON/HTML report-file rendering (`generate_gitlab_reports`, Phase 2D-B —
   see "GitLab report-file rendering" above), and CLI wiring (`cloudops-guard audit
   gitlab`, Phase 2E-A — see "GitLab CLI integration" above) are all implemented.
   This phase is complete.
4. **Automated tests, controlled GitLab acceptance testing, documentation, and
   release preparation.** Automated tests and documentation for every phase above are
   in place. Controlled acceptance testing has passed on both GitLab.com's current
   hosted version and self-managed GitLab CE 18.4.6, at Owner and at Maintainer —
   on GitLab.com via a Maintainer-role project service account, and on self-managed
   via an ordinary, non-service-account internal user account (see "Controlled
   GitLab.com acceptance record" and "Controlled self-managed GitLab CE 18.4.6
   acceptance record" below) — this satisfies this milestone's documented v0.2.0
   scope. Other self-managed GitLab releases and editions, and the other untested
   account/token combinations listed in "Matters requiring controlled acceptance
   testing," remain outstanding for future evidence-broadening, but do not block
   this milestone. Release-candidate preparation (version bump, README/documentation
   update, packaging/build validation) is complete. Remote CI passed on commit
   `ac75c487b6c633c758b09f71a38b198357688edb`, the pre-release-preparation baseline —
   that commit does not include the release-preparation changes, so it does not

## G. Acceptance principles

- Tests must not contact a live GitLab server.
- Mock representative HTTP responses at the API boundary — following the same
  philosophy as `tests/fixtures/builders.py`, which builds real `kubernetes.client`
  model objects rather than hand-rolled dicts; the GitLab equivalent should mock
  realistic API response payloads, not simplified stand-ins.
- Every check requires positive, negative, boundary, and missing-field tests where
  applicable (missing-field tests matter especially here given the edition/version
  API concerns noted per-check above).
- GitLab.com and self-managed base URLs must both be supported safely.
- Minimum usable token scope and minimum project role must be **proven through
  controlled live testing**, not assumed — mirrors how v0.1.0's RBAC permissions were
  validated against a real `kind` cluster rather than inferred from documentation
  alone.
- Authentication failures, forbidden responses, rate limits, invalid JSON, timeouts,
  TLS/network failures, and pagination must all eventually fail cleanly (non-zero
  exit, sanitized message, no traceback) — mirrors the existing `CollectorError`
  posture in `src/cloudops_guard/collectors/kubernetes.py`.
- Existing Kubernetes tests and behaviour must remain unchanged throughout.

## Resolved design decisions

The following were open questions in an earlier version of this document and are now
resolved (see the referenced sections for full detail — this list is a pointer, not a
restatement):

- **Minimum supported GitLab version**: 18.4 for self-managed; GitLab.com is always
  treated as current. See "Supported GitLab versions."
- **Access contract**: `read_api` token scope, Maintainer project role (confirmed
  minimum as of 2026-08-18; Owner remains sufficient), sourced only from
  `CLOUDOPS_GUARD_GITLAB_TOKEN`. See "Authentication and minimum access."
- **`GL-SEC-002` field**: `ci_push_repository_for_job_token_allowed` (`true` =
  finding). See §C.
- **`GL-SEC-003` field**: `ci_pipeline_variables_minimum_override_role`, with
  `developer` as the only failing value among its four documented enum values;
  `restrict_user_defined_variables` is historical context only. See §C.
- **`GL-COST-001` type**: `auto_cancel_pending_pipelines` is a string
  (`"enabled"`/`"disabled"`), not a boolean. See §C.
- **`GL-COST-002` scope and condition**: limited to the project-level
  `ci_default_git_depth` default; per-job/pipeline `GIT_DEPTH` overrides are an
  explicit, documented false-negative gap for v0.2.0, not evaluated. `0` and `null`
  are both proven (Phase 2C-D1 investigation, source-traced through GitLab Runner)
  to mean unlimited/full history and both trigger the finding; `1`-`1000` pass. See
  §C.
- **Protected-branch evaluation** (`GL-BR-001` – `GL-BR-003`): paginate
  `protected_branches`, evaluate every exact/wildcard/inherited rule matching the
  default branch, and resolve multiple matches using GitLab's documented
  most-permissive-wins behavior. `allow_force_push` is available on Free, Premium and
  Ultimate — it is **not** EE-only as an earlier version of this document stated; a
  missing value on a supported version is now a hard capability/access failure, not
  "not applicable." See §C.
- **`GL-CI-001` design**: uses the CI Lint API
  (`GET /projects/:id/ci/lint` with `content_ref` for the default branch,
  `dry_run=false`, `include_jobs=false` — static validation, not pipeline
  simulation), parsing only `merged_yaml` and applying a narrow, bounded
  default/legacy/`inherit:`-aware image-resolution algorithm (not a general CI
  compiler) proven against GitLab 18.4's own source. `include_jobs=true` is never
  enabled: it does not expose per-job image/services data on any inspected version.
  Every CI Lint `404` is a sanitized collection failure for now, never reinterpreted
  as "no CI configuration." Retains only normalized project path, job name, image
  resource kind, and either a static image reference or a dynamic/unverifiable
  marker; discards everything else immediately, including for dynamic/unverifiable
  image references. See §C and "Security and privacy invariants."
- **`GL-MR-001` with no CI configured**: always evaluated and reported when disabled;
  never suppressed. `allow_merge_on_skipped_pipeline` remains a documented, separate
  limitation. See §C.
- **`--project` argument**: accepts a numeric ID, a human-readable full path, or an
  already URL-encoded path; the CLI performs canonical encoding internally. See §B.
- **HTTP client pagination, redirect, and TLS requirements**: documented explicitly.
  See "HTTP client requirements (pagination and transport/URL safety)."
- **Combined GitLab evaluator**: `evaluate_gitlab`, in the existing shared
  `src/cloudops_guard/engine/evaluator.py` (not a separate GitLab evaluator module),
  identity-binds its two input snapshots through exact `project_path` equality (never
  by `collected_at`), and combines findings in a documented stable order
  (protected-branch, then project-setting, then timeout, then CI-image). See
  "Combined GitLab evaluator" above.
- **GitLab report-file rendering**: `generate_gitlab_reports`, in the existing shared
  `src/cloudops_guard/reports/generator.py` (not a separate GitLab report module),
  with its own `gitlab_report.html.j2` template (the released `report.html.j2` is
  unchanged). JSON preserves `evaluate_gitlab`'s finding order exactly; HTML groups
  findings by severity (Critical → High → Medium → Low) while preserving each
  group's relative order. See "GitLab report-file rendering" above.
- **GitLab CLI integration**: `cloudops-guard audit gitlab` requires all four of
  `--gitlab-url`/`--project`/`--job-timeout-threshold-seconds`/`--output` (no
  `--token`/`--config`/`--insecure`); validates the URL and project *before* reading
  the token or making any request; collects the project snapshot, then the CI
  snapshot bound to it by object identity, in that order; evaluates and renders
  through the existing single entry points; and never changes exit status based on
  finding count. See "GitLab CLI integration" above.

  access. Normalized: `allow_force_push=true`, `role_push_access_levels=[30]`,
  `inherited=null`/`None`.
- The audit exited `0` with Critical 0, High 5, Medium 2, Low 0. The two
  additional findings appeared first in the finding order:
  1. `GL-BR-002` (High, `ProtectedBranch`, `main`)
  2. `GL-BR-003` (Medium, `ProtectedBranch`, `main`)

**Overlapping-rule test**:

- The exact `main` rule was restored to the safe baseline. A separate wildcard
  `*` rule was added, with force push enabled and Developer push access.
- The collector's normalized snapshot contained both the safe `main` rule and
  the unsafe wildcard rule.
- The audit again produced Critical 0, High 5, Medium 2, Low 0. `GL-BR-002` and
  `GL-BR-003` were attributed to the affected branch `main` — **not** to `"*"`,
  since that is not a branch name — demonstrating that the unsafe wildcard
  rule's permissions applied to the default branch despite the separate, safe
  exact rule also matching it.

**Restoration**:

- The wildcard rule was deleted, and the exact `main` rule was restored to the
  recorded safe baseline.
- A final audit returned Critical 0, High 4, Medium 1, Low 0, with finding order
  back to `GL-MR-001`, `GL-SEC-001`, `GL-SEC-003`, `GL-CI-001`, `GL-CI-001`, and
  an empty protected-branch finding list.

**Minimum-access conclusion**: on the strength of this self-managed GitLab CE
18.4.6 evidence together with the GitLab.com evidence above, this document's
documented minimum role for the implemented GitLab audit is now **Maintainer**
with `read_api`, not Owner — see "Authentication and minimum access" above.
Owner remains sufficient; it was tested successfully here too. This conclusion
is bounded to what was actually tested: other self-managed GitLab releases or
versions, and GitLab Enterprise Edition and its Premium/Ultimate tiers, remain
unverified. On self-managed GitLab, account/token combinations other than the
tested ordinary internal accounts using legacy personal access tokens remain
unverified. The separately tested GitLab.com Maintainer project-service-account
configuration is documented above. See the updated "Matters requiring controlled
