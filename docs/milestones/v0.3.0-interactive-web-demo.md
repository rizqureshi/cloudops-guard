## A. Purpose and product objective

**Objective**: create a polished public website where prospective customers can
explore CloudOps Guard's released Kubernetes and GitLab capabilities using
synthetic data, and where users can inspect one or compare two existing CloudOps
Guard `report.json` files entirely inside their browser.

**This is not the multi-tenant SaaS platform.** It is a marketing and evaluation
surface for the released CLI product. The website must not connect to customer
Kubernetes clusters, GitLab instances, cloud accounts, or any other
customer-controlled infrastructure. Every interactive demonstration on the site
uses synthetic data prepared and committed as part of this milestone (see §H);
every "explorer" interaction operates only on a `report.json` file the visitor
selects from their own device, processed only in their own browser (see §F, §L).

## B. Approved technology stack

- **Astro** for the static public site and routing.
- **React islands** for interactive report dashboards (demo pages, the local
  report explorer, comparison view) — not for the whole site.
- **TypeScript in strict mode**, throughout.
- **Zod** for runtime validation of user-selected JSON (both the synthetic demo
  data and any report a visitor imports).
- **npm** with a committed `package-lock.json`.
- **Node.js 24 LTS** as the initial implementation baseline.
- **Project-owned CSS**: CSS variables, global styles, and component styles
  authored for this project.
- **No large UI framework initially** (no MUI, Chakra, Tailwind component
  library, etc.).
- **No chart library initially**; severity and comparison visualizations are
  built from accessible HTML/CSS/SVG — the visualizations in scope for v0.3.0
  (severity bars/counts, new/persistent/resolved comparison indicators) do not
  need a charting dependency.
- **React hooks and pure TypeScript utilities** for state; no Redux or
  similar global-state library — the state (imported report(s), active
  filters/search/sort, comparison mode) is local to the report-workspace
  island and does not need cross-page global state.
- **Vitest** and **React Testing Library** for unit/component testing.
- **Playwright** for end-to-end and cross-browser testing.
- **Playwright plus `axe`** (`@axe-core/playwright`) for automated
  accessibility checks.
- **Cloudflare Workers Static Assets** as the intended hosting architecture.
- **Only narrowly isolated Worker endpoints** for contact and feedback (§M) —
  every other route is served as a static asset with no Worker code invoked.
- **Production deployment must be manual and explicitly authorized** (§N) —
  never automatic on push or merge.

**Why no Python web server, report-upload API, database, authentication system,
or early SaaS backend**: the product objective (§A) is explicitly a static
marketing/evaluation site with entirely browser-local report processing, not an
early increment of the eventual multi-tenant SaaS platform. Introducing a
server-side report-processing path, persistence, or auth would (a) contradict the
"reports are never uploaded" privacy promise this milestone exists partly to
demonstrate (§L), (b) pull in exactly the dependencies `CLAUDE.md` says not to
add before a milestone requires them (database, web framework, auth), and (c)
duplicate work that belongs to a future, explicitly scoped SaaS milestone rather
than being backed into this one. The Python package (`cloudops_guard`) and its
CLI, models, checks, collectors, and report generation are entirely unaffected by
and unused by the website — the website only ever reads a `report.json` file a
human already produced by running the existing CLI.

## E. Report-contract preservation

The released report contracts are **immutable for this milestone**:

- Kubernetes `AuditReport` (`src/cloudops_guard/models.py`) remains unchanged and
  has **no platform discriminator** field.
- GitLab `GitLabAuditReport` remains a **separate** model with
  `platform: "gitlab"` (a fixed `Literal`).
- Existing `report.json` and `report.html` output (both Kubernetes and GitLab)
  must not change — the golden fixtures
  (`tests/fixtures/golden_kubernetes_report.json`,
  `tests/fixtures/golden_gitlab_report.json`) remain byte-for-byte authoritative
  and unchanged by this milestone.
- v0.3.0 must not introduce a shared Python report base class, a `platform`
  field on `AuditReport`, or any other refactor of the released models. All
  platform-detection and normalization logic for the website lives in
  TypeScript, in the browser, operating on the JSON these models already
  produce — never in Python, and never by changing what Python produces.

**Two browser-side parsers**, defined for a later implementation phase (not
created now):

- `parseKubernetesReport(json: unknown): NormalizedWebReport` — validates
  untrusted JSON against the Kubernetes `AuditReport` shape (Zod schema mirroring
  `AuditReport`/`Finding`/`AuditSummary`) and converts it.
- `parseGitLabReport(json: unknown): NormalizedWebReport` — validates untrusted
  JSON against the `GitLabAuditReport` shape (Zod schema mirroring
  `GitLabAuditReport`/`GitLabFinding`/`AuditSummary`, discriminated by
  `platform: "gitlab"`) and converts it.

Platform detection for an arbitrary imported file is structural: the presence of
`platform: "gitlab"` selects the GitLab parser; its absence combined with a
successful match against the Kubernetes `AuditReport` shape (which has no
`platform` field at all) selects the Kubernetes parser. A file matching neither
shape is rejected (§F).

**`NormalizedWebReport`** (the internal browser-only representation both parsers
produce):

- Is **not** a new CloudOps Guard CLI report format — it has no relationship to
  `report.json`'s schema beyond being derived from it.
- Is **never** written back into `report.json` or any file.
- Is **never** sent to a server (see §L).
- Must not require any change to the Python models in `src/cloudops_guard/models.py`.
- Must retain enough of the original data to present every supported finding
  field accurately (check ID, title, severity, resource identity fields specific
  to each platform, evidence, impact, recommendation, `auto_remediable`,
  `audited_at`, and the report-level identity/summary/timestamp fields) — it is
  a superset/union view for display purposes, not a lossy summary.

## F. Local report import

Exact v0.3.0 limits:

- **JSON files only** (`.json`; `report.html` is never accepted — see below).
- **One report** for single-report exploration.
- **Up to two reports** for comparison.
- **Maximum 10 MiB per file.**
- **Maximum 10,000 findings per report.**
- Only the **currently released** Kubernetes and GitLab JSON contracts (§E) are
  supported — no versioned-schema negotiation, no legacy-format support.
- Every timestamp (`generated_at`, `audited_at`) must be a **valid,
  timezone-aware** timestamp; a naive or malformed timestamp is rejected.
- **Severity counts are recomputed from `findings`**, never trusted from the
  file's `summary` object as given.
- **A report is rejected if its supplied `summary` disagrees with the
  recomputed counts** — this both catches a hand-edited or corrupted file and
  avoids ever displaying a summary that doesn't match the findings shown.
- Malformed, oversized, ambiguous (matching neither known contract, or
  ambiguously matching characteristics of both), or otherwise unsupported files
  are rejected with a clear, sanitized error.
- **Mixed-platform comparisons are rejected** (a Kubernetes report cannot be
  compared against a GitLab report).
- **Comparisons between different target identities are rejected** (§G defines
  target-identity compatibility precisely).
- **No arbitrary folders or multi-report history** — the browser never reads a
  directory, and no more than two reports are ever held at once (§L: browser-tab
  memory only, cleared on reload/close).
- **`report.html` is never imported** — only `report.json`. The website does not
  parse, execute, or otherwise process HTML report files.
- **Never accepts** a kubeconfig file, a GitLab token, CI YAML, or any other
  credential-shaped input — the file picker and its validation only ever
  recognize a `report.json`-shaped JSON document; nothing else is a valid
  selection.

Import/validation errors must be **sanitized and useful** without reproducing
large or potentially sensitive report values in the error message (e.g. "This
file doesn't match a supported CloudOps Guard report format" rather than dumping
raw parsed JSON or oversized field values into the UI).

## G. Comparison semantics

**Deterministic comparison statuses**, computed entirely client-side:

- **New**: a finding present only in the newer report.
- **Persistent**: a finding present in both reports.
- **Resolved**: a finding present only in the older report.

"Newer"/"older" is determined by `generated_at`: the comparison requires the
older report's `generated_at` to strictly precede the newer report's
`generated_at`. Two reports with equal or reversed timestamps are rejected as an
invalid comparison pair rather than silently guessed at.

**Multiset/bag matching**, not plain set matching: if a fingerprint (below)
occurs more than once within a single report, duplicate occurrences are matched
pairwise between the two reports (up to the smaller count), so that, for
example, two identical fingerprint occurrences in the older report against one
in the newer report correctly yields one persistent and one resolved finding —
never silently collapsed to a single comparison outcome.

**Initial fingerprints:**

Kubernetes — `check_id + cluster_context + namespace + resource_kind + resource_name + container_name`

GitLab — `check_id + project_path + resource_kind + resource_name + job_name`

**Comparison must not depend on**: finding order, evidence wording, impact
wording, recommendation wording, the `audited_at` timestamp, or severity-count
summary ordering. Two findings with an identical fingerprint are treated as the
same finding across reports regardless of any difference in these fields.

**Known GitLab limitation, to be documented in-product, not silently smoothed
over**: because `GL-CI-001`'s fingerprint uses the image reference as
`resource_name`, changing a job's image reference (e.g. bumping a tag) will
normally appear as a **resolved** previous finding plus a **new** current
finding for that job — not as one persistent finding whose evidence changed.
The comparison UI and any accompanying copy must not silently describe this
as a single persistent finding; if this limitation is surfaced to the user,
it must be described accurately.

**Target-identity compatibility** (required for a comparison to be permitted
at all):

Kubernetes — same `cluster_context`, and same `namespace_filter` (including
`null` vs. a specific namespace string both being significant — `null`
compared against a named namespace is **not** compatible).

GitLab — same `project_id`, same `project_path`, and same recorded
`gitlab_url`, determined as follows:

- For the currently released and supported GitLab report contract,
  `gitlab_url` is the normalized instance base URL the CLI already recorded
  onto `GitLabAuditReport` at collection time (via the existing
  `normalize_gitlab_base_url`) — it is not re-derived, re-parsed, or
  re-normalized by the website.
- After each report passes schema validation (§E/§F), GitLab target-identity
  compatibility uses **exact string equality** of that recorded `gitlab_url`
  value between the two reports — a plain string comparison, nothing more.
- The browser **must not** resolve DNS, make a network request to the GitLab
  instance, or silently rewrite the scheme, host, port, or path while
  deciding compatibility — compatibility is decided entirely from the two
  already-parsed report values, with no normalization step of the website's
  own and no network access of any kind.
- Two reports whose recorded `gitlab_url` values are not exactly equal —
  including a difference the CLI's own normalization does not collapse (e.g.
  an explicit default port vs. an omitted default port, a hostname/netloc
  case difference preserved as-given, or a path-case difference — none of
  which `normalize_gitlab_base_url` folds or rewrites) — are
  **incompatible** for comparison. This is a deliberate, simple, and
  predictable rule: it never silently treats two differently-recorded URLs as
  "probably the same instance."

**No override for cross-target comparison in v0.3.0** — there is no "compare
anyway" escape hatch; an incompatible pair is simply rejected.

## H. Synthetic demonstration data

Requirements for all `/demo/kubernetes` and `/demo/gitlab` data:

- **No real customer, organization, cluster, repository, or domain** — every
  identifier is obviously fictional.
- Use **obvious fictional names** and **reserved example domains** (e.g.
  `example.com`/`example.org`/`example.net` per RFC 2606, and clearly
  fictional org/service names — following the same convention already used in
  the golden fixtures, e.g. `checkout-api`, `example.com/checkout-api`,
  `engineering/checkout-service`, `gitlab.example.com`).
- **Every synthetic view is clearly labeled** as synthetic — the "Synthetic
  demonstration" indicator from §D is always visible on these routes.
- **Deterministic, fixed timestamps** — no `Date.now()`/relative "N days ago"
  data that would make the demo non-reproducible or drift over time.
- **Multiple scan states**, sufficient to demonstrate `new`, `persistent`, and
  `resolved` comparison outcomes (§G) on both the Kubernetes and GitLab demos.
- **Every currently implemented check must appear at least once** across the
  synthetic data: **six** Kubernetes checks (`K8S-RES-001`–`004`, `K8S-IMG-001`,
  `K8S-REL-001`) and **eleven** GitLab checks (`GL-BR-001`–`003`, `GL-MR-001`,
  `GL-SEC-001`–`003`, `GL-COST-001`–`002`, `GL-REL-001`, `GL-CI-001`) —
  **seventeen checks total**.
- **Do not fabricate an implemented Critical-severity check** — the current
  product has none (the highest severity produced by any implemented check is
  High); synthetic data must not invent a Critical finding to look more
  impressive.
- **Synthetic reports must validate against the released report contracts** —
  i.e. against `parseKubernetesReport`/`parseGitLabReport` (§E), the same
  validation path a real imported report goes through. A synthetic report that
  the site's own parser would reject is a bug.

## I. Executive summary

A deterministic, non-LLM executive summary view, computed entirely from the
normalized report(s) in the browser, containing:

- Platform and target identity.
- Audit timestamp (`generated_at`).
- Total and severity counts (recomputed, per §F).
- New, persistent, and resolved counts, when comparison is active (§G).
- Important affected categories (e.g. which check categories — resource
  hygiene, image pinning, branch protection, CI security, cost — contributed
  findings).
- Up to **five** prioritized recommendations (deterministically selected —
  e.g. by severity then check-category diversity — never arbitrarily or
  randomly ordered).
- Scope and limitations (what was and wasn't audited, matching the checks
  actually run).
- A synthetic-or-local-report indicator (mirrors §D/§H).

**Explicitly excluded:**

- An arbitrary health score.
- A proprietary risk score.
- AI-generated conclusions (the summary is template-driven from the normalized
  data — no LLM call, no generative text).
- Any claim that the implemented checks provide complete Kubernetes or GitLab
  coverage.

## L. Security and privacy boundary

**Report files are untrusted input.** For `/demo/*` and `/explorer` routes:

- Report data lives in **browser-tab memory only**.
- **No report content in `localStorage`.**
- **No report content in `sessionStorage`.**
- **No report content in `IndexedDB`.**
- **No report content in cookies.**
- **No service-worker caching of reports.**
- **Reloading or closing the tab clears imported reports** — there is no
  "restore my last session" feature for report data.
- **No report-ingestion or report-upload API.** There is no server-side
  endpoint, and no application code path, that automatically transmits an
  imported report, report file, finding, summary, fingerprint, comparison
  result, or any other report-derived data. Local report processing (import,
  validation, filtering, searching, comparison, display) remains entirely
  browser-side and does not itself cause a network request. This is distinct
  from — and must not be confused with — the separately isolated
  contact/feedback endpoint (§M), which exists but accepts only a small set
  of bounded, deliberately user-entered contact fields, is architecturally
  disconnected from report data, and is never invoked automatically by report
  exploration. This document does not claim that arbitrary user-entered free
  text is technically incapable of containing report-derived content a user
  chose to type or paste — see §M for how that possibility is bounded instead
  (field allowlisting, length limits, and UI guidance not to paste sensitive
  content), rather than asserted away.
- **No analytics.**
- **No session replay.**
- **No third-party error-reporting SDK.**
- **No third-party scripts on demo/explorer routes.**
- **No `fetch`, `XMLHttpRequest`, `WebSocket`, or beacon requests** triggered
  by report import, validation, filtering, searching, comparison, or display —
  these operations are pure, synchronous (or purely local-async) client-side
  computation.
- A **restrictive, route-specific Content-Security-Policy** on demo/explorer
  routes with `connect-src 'none'`.
- **No `dangerouslySetInnerHTML`** for report content.
- **No interpretation of report strings as HTML, Markdown, CSS, or executable
  code** — every report-derived string is rendered as plain text.
- **No dynamic navigation to report-supplied URLs** — nothing in a report
  (image references, evidence text, etc.) is ever used as an `href`/redirect
  target.
- **No logging of filenames, report fields, imported values, or validation
  payloads** — client-side or server-side (there is no server-side path for
  this data at all, per §A).

**Required automated browser test**: a Playwright test covering report loading
and exploration in the local report workspace, that (1) loads the explorer
route, (2) selects a representative valid report, (3) searches, filters, opens
a finding, and performs a comparison, and (4) proves those report-loading and
-exploration operations cause **no report-related network request** (e.g.
asserting on Playwright's network-request log that nothing fired after the
initial page load completes, for the duration of those interactions). This
test's scope is the report workspace only — it does not exercise, and makes no
claim about, the contact/feedback form.

**Clarification**: normal initial loading of the website's own static HTML,
CSS, and JavaScript (the Astro-built site itself) is not a "report upload" and
is not what this boundary restricts — the restriction is on requests
*triggered by report data or report interactions*, not on the site loading at
all. Contact and feedback submission (§M) are separate, deliberate, intentional
network actions a visitor takes on a different route, outside the scope of
this no-network guarantee — the guarantee is about report handling, not about
the website having zero network capability anywhere.

## M. Contact and feedback boundary

Two isolated routes, or one shared typed endpoint, supporting:

- Demo/pilot requests (`/request-demo`).
- Feature feedback (`/feedback`).

**Permitted fields only**:

- Form type.
- Name.
- Work email.
- Company (optional).
- Message (maximum 2,000 characters) — see "Message field" below.
- Consent acknowledgement.
- Turnstile token — see "Turnstile is the sole token exception" below.

**There is no report file, attachment, report JSON, kubeconfig, GitLab token,
cloud credential, infrastructure credential, or report-import field.** The
schema above is a closed allowlist: no dedicated or supported field or
workflow exists, or may be added, for a file upload, structured report
content, a kubeconfig, a GitLab access token, a cloud-provider credential, or
any other infrastructure credential. **No customer, cloud, Kubernetes,
GitLab, or infrastructure credential/token field is permitted** in this
schema, now or in a later phase, without a fresh milestone-level decision.

**Message field**: the message is bounded, user-entered free text (maximum
2,000 characters) — nothing more structured. It:

- **Must never be automatically populated, suggested, enriched, or derived
  from an imported report** — no code path pre-fills, appends, or offers
  report/finding content into this field.
- Is rendered as plain text on submission and delivery, never interpreted as
  HTML, Markdown, or executable content (mirrors §L's report-string handling).
- Must be accompanied by **form UI copy that explicitly warns users not to
  paste secrets, credentials, tokens, report JSON, or other sensitive
  infrastructure information** into it — because it is free text a human
  types or pastes, the platform cannot technically prevent someone from
  choosing to paste something sensitive; the warning and the field's bounded
  length and plain-text handling are the mitigations, not a claim that the
  field is somehow incapable of carrying such content.

**Turnstile is the sole token exception**: a Cloudflare Turnstile anti-abuse
token, when Turnstile is used, is the one permitted token-shaped field in this
schema. It exists solely for bot/abuse mitigation, is not a customer
credential of any kind, and carries no infrastructure access.

**Requirements:**

- **No report attachment.**
- **No arbitrary file attachment.**
- **No credentials or tokens** as a field, other than the Turnstile
  anti-abuse token described above.
- **Same-origin POST only.**
- **Strict `Content-Type` validation.**
- **Small, bounded request-body size.**
- **Field allowlist and length validation** (server-side, not just client-side).
- **Origin validation.**
- **Mandatory server-side Turnstile verification** — a request without a
  verified Turnstile token is rejected.
- **No request-body or field logging.**
- **No database.**
- **Delivery to one verified CloudOps Guard email address.**
- **Mailto fallback** if delivery is unavailable.

**Architectural separation**: the contact/feedback Worker endpoint is separate
from report exploration in every sense — separate route(s), separate code
path, separate (minimal) permitted-field schema. **There must be no code path
that submits an imported report or any derived finding content to it**: the
contact/feedback schema has no dedicated or supported report, report-JSON,
report-file, attachment, credential, or report-import field; no
report-workspace code ever calls the contact/feedback endpoint; and **the
report workspace must not invoke the contact endpoint or provide an automatic
"send this report/finding" action** of any kind (no button, shortcut, or
generated link that pre-fills or transmits report/finding content to
`/request-demo` or `/feedback`). This is a guarantee about the absence of a
dedicated field and of any *automatic* code path — the bounded message field
(above) remains deliberately user-entered, arbitrary plain text, and its UI
warning, length limit, allowlisted schema, and plain-text handling mitigate a
user manually pasting report-derived content into it, without making that
technically impossible; this document does not claim otherwise.

**Privacy copy** must disclose that text a visitor **deliberately types or
pastes** into the contact/feedback form **is transmitted and retained as
email for the purpose of handling that request** — the "your report is never
uploaded" promise from §L applies specifically to user-selected report files
on demo/explorer routes, and must not be worded so broadly that it appears to
also cover contact-form submissions (which are, by design and by the
visitor's own choice, sent and retained).

9. **Phase 3I — Contact and Feedback Boundary.**
   - *Objective*: `/request-demo` and `/feedback`, backed by the isolated
     Worker endpoint(s) from §M.
   - *Included work*: form UI, Worker endpoint(s), Turnstile integration,
     email delivery, mailto fallback.
   - *Explicit exclusions*: any code path connecting these forms to report
     data (explicitly prohibited, §M).
   - *Tests/evidence required*: endpoint validation tests (allowlist, size
     limits, Content-Type, origin, missing/invalid Turnstile token all
     rejected); a static-analysis or lint check proving no import path from
     `features/report-*` into the contact/feedback code.
   - *Exit condition*: contact/feedback works and is provably isolated from
     report data.
   - *Status*: **implemented, not yet closed.** `/request-demo` and
     `/feedback` are live in the build, each hydrating exactly one
     `ContactForm` island (`client:load`). The shared contract
     (`web/src/features/contact-form/contract.ts`) allows exactly
     `formType`/`name`/`workEmail`/`company`/`message`/`consent`/
     `turnstileToken` via a strict Zod object; unknown fields, wrong
     types, over-length values, non-literal `consent`, and inappropriate
     control characters are all rejected outright (never truncated). The
     Worker (`web/worker/contact.ts`) enforces, in order: exact path
     (rejecting query-string variations) → `POST` only (`Allow: POST` on
     rejection) → exact-match `Origin` (parsed and compared to
     `request.url`'s origin, never suffix/substring/wildcard matched, no
     CORS reflection) → exact `application/json` Content-Type (no
     parameters permitted) → absent `Content-Encoding` → an 8 KiB body
     limit enforced twice (`web/worker/readBoundedBody.ts`: a declared
     oversized `Content-Length` rejected before any read, then a bounded
     incremental read that stops the instant actual bytes exceed the
     limit, covering chunked/dishonest/absent-`Content-Length` bodies
     alike; `request.text()`/`request.json()` are never called) → JSON
     parse and object-shape checks → the shared contract → mandatory
     server-side Turnstile verification
     (`web/worker/turnstile.ts`: a single POST to the real Siteverify
     endpoint, hostname- and `formType`-matched action, a bounded
     timeout, no visitor IP sent, no caching, no retry — network failure,
     non-2xx, malformed JSON, `success !== true`, and any mismatch all
     collapse to one sanitized `verification_failed` response) → email
     delivery (`web/worker/email.ts`: exactly one plain-text email via
     the structured `EMAIL.send({ to, from, subject, text })` binding;
     `to`/`from`/subject are always fixed from Worker configuration or a
     fixed per-`formType` subject table, never from submitted input, so
     no visitor-controlled header/recipient/CC/BCC/attachment is
     possible and no acknowledgement email is ever sent to the visitor).
     A binding failure returns a sanitized `503 temporarily_unavailable`
     response carrying the configured `CONTACT_TO_EMAIL` as a fallback;
     the client re-validates that value as a plain email address before
     building a `mailto:` link itself, containing only a fixed subject —
     never the visitor's name, message, or Turnstile token. Every
     response is a fixed, sanitized JSON body (`Content-Type`,
     `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`; never

     error, or a stack trace); the Worker contains no
     `console.log`/`console.error` anywhere. A dedicated contact-route
