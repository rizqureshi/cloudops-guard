**Two genuine, real cross-browser defects were found and fixed** while
building this matrix (not merely test-authoring bugs):

1. **Firefox: a stale `<input type="file">` display value survives page
   reload.** Firefox's own form-data-restoration feature (not Chromium's or
   WebKit's) re-displays a previously selected filename in a file input
   after `page.reload()`, even though no real file content is ever
   restored and the React application state was already correctly empty
   (`"No report imported yet."` was already showing). Fixed by explicitly
   clearing both file inputs' `.value` in a mount-only `useEffect` in
   `LocalReportExplorer.tsx`. Confirmed non-vacuous.
2. **Firefox: a CSP `securitypolicyviolation` console error from Zod's
   internal `eval`-availability probe.** Zod v4's fast-validation path
   probes `new Function("")` in a caught try/catch to detect JIT
   availability; Firefox still reports the blocked call as a CSP violation
   even though the exception is swallowed and nothing breaks functionally.
   Affected `/checks`, `/explorer`, `/request-demo`, `/feedback` — every
   route that validates with Zod in the browser (the two demo routes parse
   at build time, in Node, and were never affected). Fixed with a new
   `src/lib/zodJitless.ts` side-effect module calling Zod's own
   `config({ jitless: true })` — Zod's upstream code explicitly
   special-cases this exact "strict CSP" scenario. `'unsafe-eval'` was
   deliberately **not** added to any CSP. Confirmed non-vacuous.

**A third genuine defect was found and fixed**: the skip link
(`<a class="skip-link" href="#main-content">`) scrolled to `<main>` but
never moved keyboard focus there — reliably in Chromium/Firefox only via
each engine's own "sequential focus navigation starting point" heuristic,
which WebKit does not implement, so activating the skip link had **no
effect at all** for WebKit/Safari keyboard users. Fixed by adding
`tabindex="-1"` to `<main id="main-content">` in `BaseLayout.astro` (the
standard WCAG technique for this exact pattern) — confirmed via direct
probing that `document.activeElement` now becomes the `<main>` element
immediately after activating the skip link, in **all three** browsers.
A residual, narrower WebKit-only nuance remains and is recorded honestly
rather than hidden: a *second* Tab press immediately after that (not the
skip-link activation itself) returns focus to `<body>` in WebKit only,
rather than continuing into the first link inside `<main>` as Chromium and
Firefox do. This is a known WebKit engine limitation around `tabindex="-1"`
containers, not a site-code defect, does not trap the user (a further Tab
just restarts from the top of the page, identical to never having used the
skip link), and no fragile workaround was attempted for it. See the
manual-keyboard section below.
