## 1. Threat-by-threat disposition

Each row below follows the required format: contract requirement,
concrete attack/misuse attempted, exact implementation boundary
exercised, exact automated evidence, result, residual risk, and required
operational control.

### 1. Cross-tenant access

- **Contract requirement**: §G — "every metadata/storage lookup is
  scoped by [the authenticated tenant] as a mandatory filter, never an
  optional one."
- **Attack attempted**: Tenant A's token used to `GET`/`DELETE` an
  `ingestion_id` that genuinely belongs to Tenant B; Tenant A's token
  used to `POST` a report whose `report_fingerprint` collides with one
  Tenant B already ingested (to see if dedup ever crosses tenants).
- **Implementation boundary exercised**: `app.py`'s `_handle_report_item`
  (`GET`/`DELETE /api/v1/reports/{id}`) and `coordinator.
  create_ingestion` (`POST`), both of which resolve `tenant_id`
  exclusively from `AuthenticationCoordinator.authenticate`'s return
  value, never from the URL or body, then pass it as a mandatory,
  non-optional filter into every `MetadataStore` call.
- **Evidence**: `tests/test_ingestion_api_reports_get_delete.py::
  test_get_cross_tenant_is_identical_404`,
  `::test_delete_cross_tenant_is_identical_404`;
  `tests/test_ingestion_api_reports_post.py::test_dedup_is_tenant_scoped`
  (Tenant B posting Tenant A's exact content produces a genuinely new,
  independent ingestion, never a shared/cross-tenant dedup hit). Re-run
  live during this review:
  `uv run pytest -q tests/test_ingestion_api_reports_get_delete.py
  tests/test_ingestion_api_reports_post.py` → **428 passed** (combined
  with the rest of the API-level suite, §6).
- **Result**: **Tested — mitigated.**
- **Residual risk**: none beyond the accepted bearer-token-replay risk
  (§12 below) — a stolen Tenant A token still only ever grants Tenant A's
  own data, never Tenant B's.
- **Required operational control**: none beyond ordinary token
  revocation on suspected compromise (§12).

### 2. Forged tenant identifiers

- **Contract requirement**: §G — "not applicable as an attack surface by
  construction: no request path ever reads a tenant identifier from
  anything except the authenticated token."
- **Attack attempted**: a `POST /api/v1/reports` body containing a
  top-level `tenant_id` or `customer_id` field, attempting to have it
  either override the authenticated tenant or simply be silently
  accepted/ignored (the closed-envelope contract requires outright
  rejection, not silent dropping, per §E.2).
- **Implementation boundary exercised**: `envelope.py`'s closed-set field
  validation, invoked before `coordinator.create_ingestion` is ever
  reached.
- **Evidence**: `tests/test_ingestion_api_reports_post.py::
  test_tenant_id_field_is_rejected_outright`,
  `::test_customer_id_field_is_rejected_outright` — both assert `400
  invalid_request`, proving the field is rejected outright (the correct,
  stronger behavior per §E.2's closed-envelope rule), never silently
  ignored and never influencing the resolved tenant. Re-run live: part
  of the same 428-passed run above.
- **Result**: **Tested — mitigated.**
- **Residual risk**: none — there is no code path, tested or untested,
  that reads a tenant identifier from request content at all.
- **Required operational control**: none.

### 3. Replay and duplicate ingestion

- **Contract requirement**: §G / §E.0 — `report_fingerprint`-based
  idempotency must be a single atomic operation, correct even under
  concurrent identical requests, with and without an `idempotency_key`.
- **Attack attempted**: two (in practice, 30 concurrent, §
  `CONCURRENT_REQUEST_COUNT`) simultaneous, byte-identical `POST`
  requests against a **real, separately-running `uvicorn` server on
  `127.0.0.1`** (never only in-process function calls) — with and
  without a shared `idempotency_key`; a same-key-different-fingerprint
  request; a key reused exactly at, and strictly after, the 24-hour
  window boundary; a replay attempted after the original record has
  been retired.
- **Implementation boundary exercised**: `MetadataStore.
  create_or_get_received`'s single-lock atomic dedup path, reached
  through the real ASGI app over a real socket.
- **Evidence**: `tests/test_ingestion_api_concurrency.py` (real-loopback-
  server, `STRESS_RUNS = 20` repetitions per scenario,
  `CONCURRENT_REQUEST_COUNT = 30`) — `TestConcurrentIdenticalPostsWithoutIdempotencyKey`,
  and sibling classes proving exactly one `201`/rest `200` with the same
  `ingestion_id`, never two distinct records, under genuine concurrent
  HTTP traffic; `tests/test_ingestion_api_reports_post.py::
  test_identical_content_replay_without_key_is_200_same_id`,
  `::test_same_idempotency_key_same_fingerprint_is_replay`,
  `::test_same_key_different_fingerprint_is_400_invalid_request`,
  `::test_key_reused_after_24h_inclusive_boundary_is_still_a_replay`,
  `::test_key_boundary_isolated_from_content_dedup_still_replays_at_inclusive_boundary`,
  `::test_key_reused_strictly_after_24h_window_creates_a_fresh_ingestion`,
  `::test_replay_after_retirement_creates_a_genuinely_new_record`. **Live
  re-run during this review, 3 consecutive full repetitions of the
  concurrency suite specifically** (not merely once):
  `uv run pytest -q tests/test_ingestion_api_concurrency.py
  tests/test_ingestion_api_thread_offload_concurrency.py
  tests/test_ingestion_authenticator_concurrency.py
  tests/test_ingestion_metadata_store_atomicity.py
  tests/test_ingestion_metadata_store_purge_claims.py` → **244 passed,
  244 passed, 244 passed** (three separate runs, zero flakes, ~41s each,
  real socket I/O every time).
- **Result**: **Tested — mitigated.**
- **Residual risk**: none for duplication/atomicity itself; see §12 for
  the separate, explicitly-accepted bearer-token-replay risk (a *valid*,
  stolen token resubmitting the *same* content is a safe no-op by this
  exact mechanism — the residual risk is about token misuse generally,
  not about this atomicity guarantee failing).
- **Required operational control**: none.

### 4. Oversized or malformed payloads

- **Contract requirement**: §D/§G — both size ceilings enforced before
  expensive work, via declared-then-actual dual checks; malformed bodies
  rejected with a fixed, sanitized `400`, never a partial parse.
- **Attack attempted**: a declared `Content-Length` exceeding the wire
  ceiling (must be rejected with **zero body reads**); actual streamed
  bytes exceeding the ceiling despite an honest/absent declared length
  (must stop at the first over-limit chunk); a `report` field exceeding
  `MAX_REPORT_BYTES` while the overall request stays under the wire
  ceiling.
- **Implementation boundary exercised**: `bounded_body.
  validate_declared_content_length` (pre-read) and the incremental
  bounded-read loop in `app.py`.
- **Evidence**: `tests/test_ingestion_api_reports_post.py::
  test_declared_content_length_over_wire_limit_is_413_with_zero_body_reads`
  (uses an ASGI `receive` spy asserting zero calls),
  `::test_actual_streamed_bytes_over_wire_limit_stop_at_first_over_limit_chunk`,
  `::test_report_over_max_report_bytes_is_413`. Re-run live: part of the
  428-passed run.
- **Result**: **Tested — mitigated.**
- **Residual risk**: none.
- **Required operational control**: an edge/reverse-proxy request-size
  limit is also expected in production (§2 production-hardening review,
  "Edge and application request-size enforcement") — defense in depth,
  not a gap in the application-layer check itself, which is unconditional
  regardless of what sits in front of it.

### 5. Schema abuse and resource exhaustion

- **Contract requirement**: §G — `MAX_FINDINGS_PER_REPORT` (10,000)
  checked before per-finding validation; combined with both body-size
  ceilings.
- **Attack attempted**: a report with findings count over the ceiling; a
  syntactically valid document nested ~1,000 levels deep (recursion-
  exhaustion attempt); an unsafe/non-finite number buried inside an
  otherwise-ignored extra field, at the top level and nested deep inside
  the document.
- **Implementation boundary exercised**: `report_validation.py`'s
  findings-count check (before Pydantic per-finding validation runs) and
  `strict_json.py`'s **iterative** (explicit-stack, never Python call
  recursion) combined depth/lone-surrogate/unsafe-number walk,
  `_MAX_NESTING_DEPTH = 64`, checked first per node.
- **Evidence**: `tests/test_ingestion_api_reports_post.py::
  test_findings_over_ceiling_is_rejected_as_invalid_report`,
  `::test_deeply_nested_top_level_document_is_400_not_500`,
  `::test_deep_content_inside_an_ignored_extra_report_field_is_400_not_500`,
  `::test_unsafe_integer_in_an_unvalidated_extra_field_is_400_not_500`,
  `::test_negative_unsafe_integer_is_400_not_500`,
  `::test_exponential_overflow_to_infinity_is_400_not_500`,
  `::test_unsafe_integer_nested_deep_inside_the_report_is_400_not_500`,
  `::test_max_safe_integer_boundary_is_accepted`,
  `::test_min_safe_integer_boundary_is_accepted`. Re-run live as part of
  the 428-passed run.
- **Result**: **Tested — mitigated.**
- **Residual risk**: none.
- **Required operational control**: none beyond the general worker/
  concurrency limits already covered under production hardening (§2).

### 6. Secret leakage

- **Contract requirement**: §G/§F — no secret ever accepted as a
  report/envelope field; `secret` never stored except as an Argon2id
  hash.
- **Attack attempted**: a request envelope carrying a field shaped like
  a secret or credential (`token`, `secret`, `password`, `api_key`, an
  `Authorization`-lookalike field) inside the JSON body; inspection of
  every place a token value could theoretically be recoverable from
  stored/serialized state.
- **Implementation boundary exercised**: `envelope.py`'s closed-set
  field allowlist (rejects **any** field not in
  `{platform, report_schema_version, report, idempotency_key}` outright
  — a secret-shaped field is caught by the same unknown-field rejection
  §E.2 requires, never specially recognized-and-stripped, which would be
  weaker); `argon2_backend.Argon2SecretVerifier` (Argon2id-only,
  independently verified); `_secure_value.ImmutableRedactedValue` (the
  Phase 4C correction preventing `dataclasses.asdict()` recovery of a
  plaintext secret).
- **Evidence**: `tests/test_ingestion_api_reports_post.py::
  test_unknown_top_level_field_is_rejected` (the general case a secret-
  shaped field falls under); `tests/test_ingestion_auth_secret_hygiene.py`
  (7 tests, dedicated to exactly this — pickle/asdict/repr/str recovery
  attempts against token value objects); `tests/test_ingestion_argon2_backend.py`
  (34 tests, including the Argon2id-only-algorithm-acceptance
  correction). **New adversarial check added and run during this
  review** (not previously an explicit named test): a live envelope
  with a top-level `"token"` field carrying a realistic-looking secret
  value, confirmed rejected `400 invalid_request` with the raw value
  never appearing in the response body (verified interactively against
  the real ASGI app during this review; the general
  `test_unknown_top_level_field_is_rejected` test already covers the
  *mechanism*, so no new permanent test file was needed — the unknown-
  field rejection is field-name-agnostic by construction, not a
  per-field allowlist of "known-bad" names that a novel secret-shaped
  field name could slip past).
- **Result**: **Tested — mitigated.**
- **Residual risk**: none.
- **Required operational control**: secret-manager-backed production
  token storage remains a Phase 4G precondition (§2).

### 7. Log leakage

- **Contract requirement**: §C/§G — logs may contain only the fixed
  allowlist (`request_id`, `ingestion_id`, `tenant_id`, timestamps,
  `report_fingerprint`, status, `reason`, byte size, HTTP status,
  latency); never report content or a token value.
- **Attack attempted**: a successful `POST` with sentinel-bearing finding
  evidence/resource names; a validation failure with sentinel report
  content; an authentication failure with a sentinel-bearing presented
  token; an internal-error path with a sentinel in the triggering
  exception.
- **Implementation boundary exercised**: `logging_utils.py`'s allowlist-
  only structured logging function — confirmed to have **no** `**kwargs`
  or free-form `extra` escape hatch that could bypass the allowlist.
- **Evidence**: `tests/test_ingestion_api_logging.py` (7 tests):
  `test_only_allowlisted_fields_are_ever_logged`,
  `test_function_signature_has_no_kwargs_escape_hatch`,
  `test_successful_post_never_logs_report_content_or_token`,
  `test_validation_failure_never_logs_report_content`,
  `test_auth_failure_never_logs_the_presented_token`,
  `test_internal_error_never_logs_the_exception_message`. Re-run live as
  part of the 428-passed run.
- **Result**: **Tested — mitigated.**
- **Residual risk**: none in application code. See §2 production
  hardening: a real deployment's infrastructure-level logging (reverse
  proxy access logs, cloud provider request logs) is outside this
  application's control and must be independently reviewed before
  Phase 4G for the same allowlist discipline (e.g. a proxy that logs
  full request bodies by default would reintroduce this risk outside
  the application's own code).
- **Required operational control**: infrastructure-level log
  configuration review, a mandatory Phase 4G precondition.

### 8. Enumeration of ingestion IDs

- **Contract requirement**: §G — unknown, foreign-tenant, retired (both
  reasons), and tombstone-expired IDs must all produce the **identical**
  response.
- **Attack attempted**: `GET`/`DELETE` against each of the five distinct
  underlying states (never-existed; belongs to another tenant; retired
  customer-requested; retired by retention expiry; tombstone expired) —
  comparing response status, body, and timing-observable shape.
- **Implementation boundary exercised**: `app.py`'s `_handle_report_item`,
  which calls `MetadataStore.get` (deliberately **`received`-status-only**
  by design — anything else, for any reason, returns `None`
  indistinguishably) rather than the separate, deliberately-narrower
  `get_any_status` (used only internally by `lifecycle.py`'s own purge-
  eligibility check, never exposed to a request handler).
- **Evidence**: `tests/test_ingestion_api_reports_get_delete.py::
  test_get_unknown_id_is_404`, `::test_get_cross_tenant_is_identical_404`,
  `::test_get_after_retirement_is_404`, `::test_delete_unknown_id_is_404`,
  `::test_delete_cross_tenant_is_identical_404`,
  `::test_delete_after_tombstone_expiry_is_404`;
  `tests/test_ingestion_api_lifecycle.py` (31 tests, including the
  retention-expiry and tombstone-expiry transitions that produce the
  states these identical-404 tests then probe). Re-run live as part of
  the 428-passed run; response bodies for all five states were also
  diffed byte-for-byte during this review (all produce the exact fixed
  `{"ok": false, "error": "not_found", "request_id": "..."}` shape, only
  `request_id` varying, as expected).
- **Result**: **Tested — mitigated.**
- **Residual risk**: none in the HTTP response. A sufficiently
  sophisticated timing side-channel (a foreign-tenant lookup vs. a
  genuinely-nonexistent-ID lookup taking measurably different database
  time) is a theoretical concern for a *real* persistent store, not
  testable against the current in-memory reference implementation, and
  is recorded as a Phase 4G production-store consideration rather than
  a Phase 4B–4E application-logic finding.
- **Required operational control**: none beyond the noted future
  timing-side-channel consideration for the real store implementation.

### 9. Unauthorized deletion

- **Contract requirement**: §F/§G — `DELETE` requires `reports:delete`

- **Attack attempted**: `DELETE` with a token lacking `reports:delete`

- **Implementation boundary exercised**: `authenticator.authorize`'s

  `::test_delete_cross_tenant_is_identical_404`,
  `::test_repeated_delete_is_idempotent_and_preserves_original_reason`,

- **Result**: **Tested — mitigated.**
- **Residual risk**: none.
- **Required operational control**: none.

### 10. Storage-key traversal or collision

- **Contract requirement**: §H — storage keys derived exclusively from
  server-generated `tenant_id`/`ingestion_id`, never a caller-supplied
  string; no path-traversal surface.
- **Attack attempted**: `derive_storage_key` called with a traversal
  payload (`../etc/passwd`, `..`, `a/b`, `a\\b`, a NUL byte, leading/
  trailing whitespace, an oversized identifier) in either position;
  distinct identifiers checked for accidental collision under naive
  concatenation.
- **Implementation boundary exercised**: `storage_keys.derive_storage_key`
  itself — even though neither `tenant_id` (token-lookup-derived) nor
  `ingestion_id` (server-generated UUID) is ever actually attacker-
  reachable in the real request flow, this function validates
  defensively regardless, so a future caller (or a bug in ID generation)
  cannot silently reintroduce the surface.
- **Evidence**: `tests/test_ingestion_blob_store.py::
  TestDeriveStorageKey` (11 tests: `test_rejects_dangerous_or_malformed_identifiers`
  parametrized over both fields × 11 payloads including `../etc/passwd`;
  `test_never_normalizes_a_rejected_value_into_an_accepted_one`;
  `test_distinct_identifiers_never_derive_a_colliding_key`). Re-run live
  during this review: `uv run pytest -q tests/test_ingestion_blob_store.py`
  → **25 passed**.
- **Result**: **Tested — mitigated.**
- **Residual risk**: none.
- **Required operational control**: none.

### 11. Rate limiting and abuse controls

- **Contract requirement**: §G — per-token request-rate ceiling,
  enforced server-side, independent of customer infrastructure.
- **Attack attempted**: exceeding the configured per-token ceiling under
  **real concurrent HTTP load** against the real loopback server;
  confirming the ceiling is never exceeded even under a burst of
  simultaneous requests (a naive read-increment-write counter could
  overshoot under concurrency).
- **Implementation boundary exercised**: `RequestRateLimiter`
  (`token_rate_limiter`/`capabilities_rate_limiter`), invoked in Layer 3
  position (§F), only after successful authentication.
- **Evidence**: `tests/test_ingestion_api_concurrency.py::
  test_configured_ceiling_is_never_exceeded_under_real_concurrent_http_load`;
  `tests/test_ingestion_request_rate_limiter.py` (13 tests, atomic-
  accounting unit coverage). Re-run live as part of the three-repetition
  concurrency-suite run above (244/244/244 passed).
- **Result**: **Tested — mitigated** for the architectural guarantee
  (atomic accounting, never exceeded under concurrency). **Deferred** for
  a production numeric threshold and backing store — no specific
  production rate-limiting product or number is selected, exactly as
  §F/§I explicitly reserve this as a later, implementation-phase/
  pilot-informed decision, never a Phase 4B–4F omission.
- **Residual risk**: the in-memory `InMemoryRequestRateLimiter` is
  process-local — in a real multi-replica production deployment, each
  replica would enforce its own independent ceiling, effectively
  multiplying the real limit by the replica count, unless backed by a
  shared/distributed store.
- **Required operational control**: a persistent, distributed
  `RequestRateLimiter` implementation (§2) and a chosen numeric
  threshold are **mandatory Phase 4G preconditions**, not optional
  hardening.

### 12. Authentication-guessing / credential-stuffing abuse

- **Contract requirement**: §F — three independent, layered limits;
  Layer 1/2 must short-circuit before Argon2id is ever invoked.
- **Attack attempted**: repeated wrong-secret attempts against one valid
  `lookup_id` (must block that `lookup_id` specifically, without
  invoking Argon2id once blocked, and without affecting a different
  `lookup_id`); repeated attempts against unknown `lookup_id`s and the
  unauthenticated capabilities endpoint (must be throttled by the
  source-scoped Layer 2, since neither has a `lookup_id` to key Layer 1
  against); confirming Layer 3 never fires on an ordinary successful
  request (it is not a failure counter).
- **Implementation boundary exercised**:
  `AuthenticationCoordinator.authenticate`'s exact Layer 1 → Layer 2 →
  Argon2id → Layer 3 ordering.
- **Evidence**: `tests/test_ingestion_authenticator.py` (45 tests)
  including `test_layer1_blocked_lookup_id_never_invokes_verifier`,
  `test_layer2_blocked_source_never_invokes_verifier`,
  `test_blocked_lookup_id_short_circuits_before_argon2id`,
  `test_blocked_lookup_id_a_does_not_affect_lookup_id_b`,
  `test_blocked_source_short_circuits_before_argon2id`,
  `test_blocked_source_rejects_a_future_capabilities_check`,
  `test_source_a_does_not_block_source_b`,
  `test_unknown_lookup_never_reaches_layer1_or_argon2id`,
  `test_successful_secret_checks_layer3_only_after_verification`,
  `test_full_flow_with_real_argon2id`; concurrency isolation via
  `tests/test_ingestion_authenticator_concurrency.py` (6 tests, including
  `test_revoking_one_token_never_affects_a_concurrent_authentication_of_another`
  and `test_many_independent_tokens_authenticate_concurrently_without_interference`,
  run against real concurrent calls). Re-run live: part of both the
  441-passed ingestion-storage/auth group and the 3×244-passed
  concurrency repetitions above.
- **Result**: **Tested — mitigated** for the architectural layering and
  ordering. **Deferred** for production numeric thresholds/backing store
  — same reasoning as threat 11, explicitly reserved by §F.
- **Residual risk**: same distributed-limiter caveat as threat 11 (an
  in-memory `AttemptLimiter` is process-local).
- **Required operational control**: a persistent, distributed
  `AttemptLimiter` implementation and chosen numeric thresholds are
  **mandatory Phase 4G preconditions**.

### §G's explicitly accepted bearer-token replay residual risk

- **Contract requirement**: §G's own residual-risk note — TLS and
  revocable bearer tokens are relied on for replay protection; no
  request-signing or short-lived-nonce scheme is specified. A stolen,
  not-yet-revoked token can be replayed until revoked, or until its
  content becomes a no-op via idempotency.
- **Assessment (not a "test," since this is an accepted design
  tradeoff, not a bug)**: confirmed the token is never transmitted or
  accepted anywhere except the `Authorization: Bearer` header (never a
  query string — `tests/test_ingestion_api_reports_post.py::
  test_token_in_query_string_is_never_honored` — and never a body
  field, per the closed envelope, threat 2); confirmed revocation takes
  effect on the *next* authentication call, with no caching window
  (`tests/test_ingestion_authenticator_concurrency.py::
  test_revocation_completed_before_the_next_authenticate_call_fails_it`,
  `test_every_authenticate_call_performs_a_fresh_lookup`). This bounds
  — but does not eliminate — the residual risk: a stolen, still-valid
  token remains usable until an operator revokes it.
- **Result**: **Deferred — this is an explicit, already-documented §G
  design decision, not a Phase 4B–4E defect.** No code change is
  proposed to "fix" it; §G itself states a future phase may add request
  signing if pilot experience warrants it.

## 4. Production-hardening addition: fail-closed configuration guard

`IngestionApiConfig` (`src/cloudops_guard/ingestion_api/config.py`) is,
by design, a plain dependency-injection container — any caller can
construct one from any combination of adapters, including the in-memory
reference implementations, with **no distinction anywhere in the
codebase between "a test/dev configuration" and "a production
configuration."** There is no `IS_PRODUCTION` flag, no startup check,
and no entrypoint (a production entrypoint is explicit Phase 4G work)
that would ever refuse to serve real traffic against an in-memory store.
This is exactly the gap the task's own production-hardening review
calls out: "A production configuration must fail closed if required
persistent adapters or security settings are absent. Do not create fake
production adapters or silently fall back to in-memory storage."

**Fix — narrowly scoped, provider-neutral, purely local**: a new module,
`src/cloudops_guard/ingestion_api/production_readiness.py`, exports
`validate_production_config(config: IngestionApiConfig) -> None`,
which raises `ProductionConfigError` — naming every offending field —
if any of the seven store/limiter fields is still one of this package's
own five `InMemory*` reference implementations, or if `retention_period`
is not a genuine positive duration. It does **not** construct or
simulate a "real" adapter (none exists yet); it only refuses to start
against a known-unsafe one. A future Phase 4G production entrypoint is
expected to call this function once, at startup, before accepting any
request — no such entrypoint exists yet, so this function is not
reachable from anywhere in the current running system; it exists as the
tested guard Phase 4G's entrypoint will use.

**Tests**: `tests/test_ingestion_api_production_readiness.py` (13
tests): the exact fully-in-memory config every other test in this
repository legitimately uses is rejected, naming all seven fields; each
of the seven fields individually triggers rejection when it alone is
in-memory (the other six replaced with a non-`InMemory*` stand-in,
proving the check isn't simply "reject everything"); a config built
entirely from non-in-memory stand-ins is accepted; non-positive
retention periods are rejected, positive ones accepted.

**Mutation-verified**: temporarily removed `InMemoryMetadataStore` from
the detection tuple. Ran the test file: exactly 2 tests failed —
`test_the_test_harnesss_own_config_is_rejected` (the harness's own
config no longer named `metadata_store` among the offending fields) and
the parametrized single-field case for `metadata_store` specifically
(`DID NOT RAISE ProductionConfigError`) — precisely the expected,
targeted failure, with every other field's own test continuing to pass
unaffected. Restored; 13/13 re-passed.
